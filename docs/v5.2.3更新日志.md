# v5.2.3 更新日志

## 上下文压缩失忆问题全面修复（自动压缩后 agent 丢失记忆）

### 背景 / 根因排查

用户报告：cbhcli-jupyter 插件中**自动压缩后 agent 失忆**（不记得任务/进度），手动压缩却正常。通过挖掘真实压缩备份（`~/.cbhcli/agents/*/history/compressions/*.json`）还原事故现场，确认了一个历史根因 + 六个当前残留问题：

**历史根因（v5.1.8 已修复，本次排查确认）**：`be45de18` 会话（2026-08-06，glm-5.2）备份显示，自动压缩生成的"摘要"内容是 `[压缩失败: API请求失败: 400 ... max_tokens expected <= 128000, but got 149685]`——摘要预算（窗口30%−保留token≈149,685）超过 API 输出上限 128,000 → 400 → 旧版把失败占位文本当摘要插入会话，顶替掉全部中间历史 → 彻底失忆。v5.1.8 已通过 SUMMARY_MAX_TOKENS 封顶 + 失败抛异常修复。

**当前残留问题（本次全部修复）**：
1. **恢复历史会话丢弃摘要**（最严重）：`/resume`、`/api/chat/load`、jupyter `ChatLoadHandler` 加载历史时跳过**所有** role=system 消息，把 `[历史对话摘要]` 也丢了——压缩过的会话一恢复就失忆。已验证真实历史文件含摘要，旧逻辑恢复后摘要消失。
2. **摘要请求继承主模型 thinking/reasoning_effort**：思考模型的 reasoning token 计入摘要 max_tokens 预算，耗尽预算时 content=None → 压缩失败；高强度思考 + 非流式还易超 API_TIMEOUT(120s)。
3. **压缩失败无冷却**：ReAct 循环每轮开始都检查压缩，系统性失败时每轮白打一次摘要 API。
4. **摘要预算未受模型配置 max_tokens 约束**：SUMMARY_MAX_TOKENS=65536 仍高于部分模型输出上限（如配置 max_tokens=32000 的模型）→ 系统性 400。
5. **空摘要不校验**：API 返回空内容时会插入空摘要 → 静默失忆。
6. **摘要与保留消息可能矛盾**：摘要模型只看 middle，看不到保留的 recent，"当前状态/下一步"可能与保留消息冲突（真实案例：摘要称 echart"未生成"，recent 里已生成）。
7. **摘要措辞无强调**：以普通 system 消息插入，模型可能忽视（真实案例：glm-5.2 面对完整摘要仍声称失忆）。

### 改动

1. **`context/compressor.py`**：
   - 新增 `SUMMARY_MARKER = "[历史对话摘要]"` 常量（摘要消息首行标记，恢复历史时据此保留）+ `MIN_SUMMARY_CHARS = 20`。
   - 空/过短摘要视为失败（`last_error` 记录，不插入会话）。
   - 摘要 max_tokens 再封顶到模型配置的 max_tokens（`llm_client.max_tokens`，若设置）。
   - 摘要请求显式关闭思考模式：模型配置了 thinking 时传 `thinking={"type":"disabled"}`（未配置的 API 不受影响）。
   - 摘要输入末尾附上保留的 recent 消息概要（`【以下最近消息被原样保留...】`），提示词要求第 8/9 章节与之一致。
   - 摘要消息措辞强化：`【重要】...这份摘要就是你对早期对话的完整记忆...禁止声称自己失忆...`。
2. **`core/model.py`**：新增模块级 `_is_thinking_disabled()`；`chat()`/`chat_stream()` 检测到 kwargs 显式传入 disabled 的 thinking 时，自动从 payload 移除冲突的 `reasoning_effort`（DeepSeek 400: thinking disabled 时不能携带 reasoning_effort）。
3. **`core/ai_handler.py`**：`process_request` 重置 `_compress_failed_this_request` 标记；`_check_and_compress_in_react` 失败后置位，本请求内不再重试（下一请求重新尝试）。
4. **`web/server.py`**：`_react_loop` 同样加 `compress_failed` 冷却；`chat_load` 恢复历史时保留 `SUMMARY_MARKER` 开头的 system 消息（只跳过旧主系统提示）。
5. **`commands/session_cmd.py`**：`/resume` 不再用 `session.reset()`（会保留当前会话全部 system 消息导致旧摘要泄漏），改为只保留 messages[0] 主提示；加载历史消息时保留摘要、跳过旧主提示。

### 效果
- 压缩过的会话通过 `/resume`、Web/Jupyter 历史恢复后，摘要完整保留，agent 不再失忆。
- 思考模型（deepseek-v4 系列等）的自动压缩不再因思考耗尽预算/超时而失败。
- 输出上限小的模型不再系统性压缩失败。
- 压缩失败不再每轮重试浪费 API；空摘要不再静默污染上下文。

### 验证
- 26 项模拟压缩测试全部通过：thinking 关闭 + reasoning_effort 移除、非 thinking 模型不带参数、空/短摘要拒绝、max_tokens 封顶、措辞强化、recent 参考段、失败保持原样、`_is_thinking_disabled` 7 用例。
- 真实压缩历史文件恢复测试：新逻辑保留摘要（旧逻辑丢失）；`/resume` 主提示保留逻辑正确。
- 端到端：jupyter 8899 `chat/load` 加载 297 条压缩历史，message_count=297（摘要在位，若丢弃应为 296）；cbhcli Web 18888 同样验证通过；简单聊天 SSE 流正常。
