# v5.1.2 更新日志

## 核心修复：LLM 双斜杠 Unicode 转义导致 edit 工具匹配失败

### 问题描述
当文件中包含 Unicode 特殊字符（如箭头 `→`、数学符号 `≥ ≤ ±`、项目符号 `•` 等）时，LLM 在返回 tool_calls 的 JSON arguments 中，有时会将这些字符以**双斜杠转义**形式返回（如 `\\u2192` 而非 `\u2192`）。

Python `json.loads()` 解析时：
- `\u2192`（单斜杠）→ 正确解析为 `→` ✅
- `\\u2192`（双斜杠）→ 保留为字面字符串 `\u2192`（6个字符）❌

这导致 edit 工具的 `old_str` 包含字面 `\u2192` 而非实际箭头 `→`，精确匹配失败，报错"未找到匹配的文本"。

### 根因分析
经过完整排查，`read` 工具、`edit` 工具、`model.py`、`session.py`、`compressor.py`、`response_cleaner.py` 等核心链路均**不存在字符转换逻辑**。问题出在 LLM API 返回的 JSON 序列化层面：

1. LLM 生成 `arguments` JSON 字符串时，将 Unicode 字符转义为 `\uXXXX` 形式
2. 某些情况下 LLM 错误地使用了双反斜杠 `\\uXXXX` 而非单反斜杠 `\uXXXX`
3. `json.loads("\\u2192")` 得到字面字符串 `\u2192`（6字符）而非 `→`（1字符）
4. edit 工具用这个错误的 `old_str` 在文件中查找，自然找不到匹配

### 修复方案
在 **所有 tool_calls arguments 解析点** 之后添加 `_fix_unicode_escapes()` 函数，递归遍历 arguments 中所有字符串值，将字面 `\uXXXX` 转义序列替换为实际 Unicode 字符。

修改位置：

| 文件 | 修改 | 说明 |
|------|------|------|
| `core/ai_handler.py` | +40行 `_fix_unicode_escapes()` 函数 + 1处调用 | CLI ReAct 循环解析 tool_calls arguments 后修复 |
| `web/server.py` | +23行 `_fix_unicode_escapes()` 函数 + 2处调用 | Web 端历史会话加载 + ReAct 循环解析 arguments 后修复 |

函数签名：
```python
def _fix_unicode_escapes(obj):
    """递归修复双斜杠 Unicode 转义序列：\\u2192 → →"""
    # dict → 递归每个 value
    # list → 递归每个 item
    # str  → re.sub(r'\\u([0-9a-fA-F]{4})', chr(int(hex, 16)), obj)
    # 其他 → 原样返回
```

### 修复流程示意
```
LLM 返回 arguments JSON
  → json.loads()          # \\u2192 变成字面 \u2192（6字符）
  → _fix_unicode_escapes() # \u2192 变成实际 →（1字符）
  → edit.execute()         # 正确匹配文件中的 →
```
