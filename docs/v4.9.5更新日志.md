# CBHCLI v4.9.5 更新日志 — 图片识别双模式统一

> 本次更新**统一图片识别入口**：删除 CLI 路径+关键词自动识图功能，image 工具升级为双模式——主模型支持视觉时图片直发主模型（共享会话上下文），否则调用其他视觉模型识别（fallback 链）。

---

## 一、背景：两条识图链路重合

v4.9.4 及之前存在两套并行的识图机制：

1. **app.py 自动识图**：用户输入同时包含动作词（识别/查看/看看…）+ 对象词（图片/截图…）时，程序自动正则提取路径或从上下文搜图，base64 嵌入用户消息直发主模型（仅当主模型 vision=y）
2. **image 工具**：AI 通过 Function Calling 自主调用，独立视觉模型识别后返回文本

**问题**：主模型支持视觉时两条路同时激活，自动识图已把图塞进消息，AI 还可能再调 image 工具重复识别；且系统提示词自相矛盾（"图片自动加载" vs "使用 image 工具"）。

## 二、新架构：image 工具双模式

```
image 工具调用（唯一识图入口）
  ├─ 模式1: 主模型支持视觉
  │     → 图片作为多模态 user 消息直发主模型
  │     → 共享当前会话上下文，零额外 API 调用
  └─ 模式2: 主模型不支持视觉
        → 调用其他已配置视觉模型识别（/fallback vision 优先）
        → 文本识别结果返回主模型
```

### 核心实现

1. **`ToolResult` 新增 `images` 字段**（tools/registry.py）— 工具结果携带 base64 图片的通道
2. **image 工具重构**（tools/image.py）：
   - `_load_images()` 图片加载提取为独立方法
   - `_main_model_supports_vision()` 判断走哪种模式
   - 模式1 直接返回带图 `ToolResult`（不再独立调用模型）
   - `_find_vision_models()` 移除"当前模型优先"分支（模式2下必为死代码）
3. **带图 user 消息追加**（core/ai_handler.py + web/server.py 对齐）：
   - 工具执行后检测 `result.images`，追加一条带图 user 消息
   - 采用 **user 角色**而非 tool 消息带图——OpenAI 兼容 API 中 tool 消息 content 为非标准多模态格式，user 消息兼容性最好
   - 消息文本自动携带识别需求（来自 `ToolResult.metadata["vision_prompt"]`）
4. **系统提示词改写**（core/agent.py）：消除"图片自动加载"矛盾指引，改为"调用 image 工具识别图片时，图片会以多模态消息直接发送到当前会话"

## 三、删除内容（app.py -159 行）

| 删除项 | 说明 |
|--------|------|
| run() 主循环图片检测块 | `supports_vision` 判断 + 路径提取 + base64 加载 |
| `_extract_image_paths()` | 动作词×对象词意图检测 + 正则路径匹配 |
| `_search_images_in_context()` | 上下文搜图（当前目录/这些/所有/文件名模糊匹配） |
| `_load_images_as_base64()` | 图片加载方法（image 工具已有等效逻辑） |
| `_handle_ai_request`/`process_request` 的 images 参数 | CLI 不再有图片来源 |
| `import re` / `import base64` | 随删除代码失去用途 |

## 四、保留不变

- **Web 端 `/api/chat/upload` 上传图片直发**：用户显式上传附件直发主模型的链路保留
- **`Message.images` 多模态管道**：session.py to_dict() 多模态序列化继续服务于上述两条链路
- **模型配置 `vision` 标志**：image 工具模式判断与视觉模型筛选的依据

## 五、子 Agent 自动继承

子 Agent 复用 `AIHandler` 的 ReAct 循环，带图消息追加逻辑自动生效，无需额外改动。
