# CBHCLI v5.4.5 更新日志

发布日期：2026-10-22
主题：上下文自动压缩失败修复（摘要预算下限 / 保留部分 token 预算 / 超时 / 诊断）

## 背景

用户在使用思考模型（qwen3 系列，本地 vLLM / 内网 256k 模型）时，自动压缩报错：

```
压缩失败: 模型未返回正文内容（finish_reason=length，思考内容 1976 字符，
max_tokens=512，思考可能耗尽输出预算）
```

排查结论（三层叠加）：

1. **摘要预算被夹到下限 512**：`预算 = 目标(窗口×30%) − 保留部分`。当
   "系统提示 + 最早2轮 + 最近3轮"已经吃掉目标时，预算变成负数，被
   `max(512, ...)` 兜到 512。实测 tushare 有会话 kept=88,140 / 89,989 / 92,968
   （窗口 128k，目标 38,400）→ 预算恒为 512。
2. **512 容不下思考**：思考模型的 reasoning token 也计入 `max_tokens`，
   512 在思考阶段就被耗尽 → `content=null` → 压缩失败。
3. **保留部分无 token 预算**：旧实现按"消息条数"保留最近 3 轮，不看大小。
   一轮里只要有一次大文件读取 / 长日志 / 大脚本生成（assistant 的
   tool_calls 参数可能几万 token），kept 就能到 88k，压缩后几乎没变小，
   很快再次触发压缩。

另外，`chat()` 的 `finish_reason=length` 重试只翻倍一次（512→1024），
且报错信息里显示的是**最初**的 512（而不是重试后的值），误导排查。

## 改动

### 1. 摘要预算下限：512 → 按窗口自适应（8192 上限）

`cbhcli_pkg/core/constants.py`：

| 常量 | 值 | 说明 |
|---|---|---|
| `SUMMARY_MIN_TOKENS` | 8192 | 预算下限上限 |
| `SUMMARY_MIN_TOKENS_FLOOR` | 1024 | 极小窗口保底 |

实际下限 = `min(8192, 窗口/16)`，最低 1024：

| 窗口 | 压缩目标（30%） | 摘要预算下限 |
|---|---|---|
| 8k | 2400 | 1024 |
| 32k | 9600 | 2000 |
| 128k | 38400 | 8000 |
| 256k | 76800 | 8192 |
| 600k / 1M | 180000 / 300000 | 8192 |

> 预算是 `max_tokens`（允许写多长），不是"一定写满"。实际摘要通常 1~2k token。

### 2. 保留部分 token 预算（目标 × 60%）+ A 方案截断

`cbhcli_pkg/core/constants.py`：`KEEP_BUDGET_RATIO = 0.6`
`cbhcli_pkg/context/compressor.py`：`_cap_kept_messages()` / `_cap_text()` / `_cap_tool_calls()`

- 保留预算 = `target × 60%`，单条消息上限 = 保留预算 / 10
- 保留部分超预算时**先减少保留轮数**（最近 3→2→1，移出的消息进入摘要范围）
- 超大内容截断规则（**A 方案**，避免误伤关键信息）：

| 角色 | 截断策略 |
|---|---|
| user | **永不截断**（用户指令原样保留） |
| assistant | 上限放宽 2 倍；正文、`reasoning_content`、`tool_calls` 参数都截断（保留 id/name，tool 消息配对不失效） |
| tool | 按单条上限截断（超大输出基本都在这里） |

- 截断方式：保留头 70% + 尾 30%，中间插入 `...[压缩时截断 N 字符]...`
- 截断只作用于"压缩成功后进入新会话的副本"，**压缩失败时原会话不受影响**

### 3. 摘要请求超时：120s → 300s

`SUMMARY_TIMEOUT = 300`。大窗口模型摘要输入可达十几万 token，沿用
`API_TIMEOUT=120s` 容易超时。模型配置可用 `summary_timeout` 覆盖。

### 4. 模型配置新增两个可选字段

```json
{
  "name": "内网-256k",
  "summary_max_tokens": 16384,
  "summary_timeout": 300
}
```

- `summary_max_tokens`：该模型的摘要输出上限（默认取 `max_tokens`，
  再封顶 `SUMMARY_MAX_TOKENS=65536`）
- `summary_timeout`：该模型的摘要请求超时秒数

### 5. 400（max_tokens 超 API 上限）自动减半重试

`_generate_summary()` 捕获 400 且错误信息含 `max_tokens/range/exceed/limit`
时，自动减半重试（最多到 1024），成功后把可用值缓存在进程内
（按 `base_url + model`），后续压缩不再撞墙。

### 6. `chat()` 阶梯翻倍重试 + 报错显示最终值

`cbhcli_pkg/core/model.py`：

- 空正文 + `finish_reason=length` 时按 512→1024→2048→4096→8192 阶梯翻倍
  （最多 4 次，封顶 `min(SUMMARY_MAX_TOKENS, 模型 max_tokens)`）
- 报错信息带上**完整的重试链**，例如：
  `max_tokens=8192，已重试 max_tokens 512→1024→2048→4096→8192`

### 7. 压缩失败诊断信息

失败时 `last_error` 附带本次压缩的关键数字：

```
模型未返回正文内容（finish_reason=length，思考内容 1976 字符，max_tokens=8192）
（本次压缩：目标 76,800，保留 76,288，摘要预算 8,192）
```

### 8. 防御：压缩后没变小则放弃

若压缩结果 token 数 ≥ 压缩前（会话本身很小、或系统提示已超过目标），
直接放弃并记录 `压缩后未变小（X → Y tokens），已放弃本次压缩`，
避免"压缩"反而把上下文撑大。正常触发压缩（≥80% 窗口）时不会发生。

### 9. reasoning 通道抢救（vLLM reasoning parser 场景）

**现象**：升级后仍报

```
模型未返回正文内容（finish_reason=stop，思考内容 2111 字符，max_tokens=8000）
（本次压缩：目标 38,400，保留 51,438，摘要预算 8,000）
```

`finish_reason=stop`（不是 length）说明**不是预算不够**——模型已经完整输出，
但部分 vLLM 部署（`--reasoning-parser qwen3` + 模板预填空 think 块）会把
**正文整段归到 `reasoning` 字段**，`content=null`。

**修复**（`LLMClient` 新增 `EmptyContentError` 携带 reasoning 原文，
`ContextCompressor._summary_from_reasoning` 做抢救）：

- `content` 为空但 `reasoning` 非空时：
  - 优先提取 `<summary>...</summary>` 块（实测思考内容里就是完整 9 章节摘要）；
  - 否则要求命中 ≥2 个章节关键词（任务目标/文件变更/当前状态/下一步…）
    且长度 ≥100 字符，去掉 `<analysis>` 块后使用；
  - 都不满足 → 维持失败（**绝不把"纯思考"当摘要塞进会话**）。
- 该抢救只用于摘要请求，不影响主对话。

**验证**：本地 vLLM qwen3.8-27b 真实端到端：20480 → 4297 tokens，
摘要 922 字符且包含 9 章节内容。

## 补充修复（同版本迭代）：同一模型 ID 多配置的"当前模型"识别（CLI）

> 用户反馈：「两个模型 ID 相同但名称不同、配置不同时，`/model list` 会同时给两个条目
> 打上『当前使用』箭头；下方状态栏显示的模型名实际是模型 ID，而不是配置名称。
> 我想配置同一模型的两套参数（一个有思考一个无思考），但 CLI 里两个都显示选中。」

**根因**：CLI 判断"当前使用哪个模型"用的是 `app.llm_client.model_name`
（= 配置里的 `model` 字段，即**模型 ID**），而模型配置的唯一键是 `name`（配置名）。
同一模型 ID 配置多份（不同 `thinking` / `temperature` / `max_tokens`）时，
按 ID 比较必然同时命中多个条目 → 重复箭头；状态栏同样取 `model_name` → 显示模型 ID。

**修复**（配置名才是模型配置的唯一标识，模型 ID 仅用于 API 请求 / token 计数）：

| 文件 | 改动 |
|---|---|
| `core/model.py` | `LLMClient` 新增 `config_name`（= `model_config["name"]`，缺省回退模型 ID），与 `model_name`（模型 ID）分开 |
| `commands/model_cmd.py` | `/model list` 与 `/model` 选择菜单的"当前"标记改按 `m["name"] == config_name`；`/model info` 的"名称"优先取 `config_name`；`/model config` 的"当前正在使用此模型，重启后生效"提示改按配置名判断（此前同 ID 两份配置都会收到提示） |
| `core/input_box.py` | 底部状态栏"模型:"显示配置名（回退模型 ID） |
| `core/app.py` | 欢迎面板信息行显示配置名（回退模型 ID） |
| `commands/session_cmd.py` | `/ctx` 的"📊 模型:"显示配置名（回退模型 ID） |

**不改动**：系统提示中注入给模型的"当前使用的模型"仍是模型 ID（模型自身能力/身份
描述需要真实模型标识）；Web / Jupyter 端本就以配置名为会话模型标识，无需改动。

**验证**（真实 CLI pty 冒烟 + 伪造 HOME 隔离，配置两个同 ID 模型：
`deepseek-flash-有思考` / `deepseek-flash-无思考`）：

- `/model list` 仅一个"◀ 当前使用"且落在正确配置；`/model use` 切换后标记同步跟随
- `/model info`：名称=配置名、模型 ID=`deepseek-flash`（真实 ID）
- 状态栏、欢迎面板、`/ctx` 均显示配置名
- 单元断言（`LLMClient.config_name` / 列表标记唯一 / 状态栏块内容）全过

## 明确不做的事

- **不关闭思考**（用户要求）：摘要请求仍使用 `skip_thinking=True`
  （不携带 thinking / reasoning_effort），不探测、不强制 `thinking=disabled`
  —— 兼容不支持关闭思考的服务商。思考模型通过"提高预算 + 阶梯重试 + 超时放宽"
  来兼容。

## 兼容性

- 用户配置无需改动即可生效（下限/超时/截断都有默认值）
- 未配置 `max_tokens` 的模型：上限仍为 `SUMMARY_MAX_TOKENS=65536`，
  撞 400 时自动减半并缓存
- 小窗口模型：下限自动缩小（`窗口/16`，最低 1024），不会出现"摘要比窗口还大"
- 对"好模型"（大窗口 / 输出上限充足）：预算本来远大于下限，唯一可能触发的是
  超大 tool/assistant 消息截断；窗口越大单条上限越大（1M 窗口 ≈ 18k token/条），
  正常对话基本不会触发

## 验证（离线模拟，不调用真实 API）

| 用例 | 结果 |
|---|---|
| 128k，最后一轮 30k token 工具输出 | 压缩成功，工具输出头尾截断，user 消息 0 条被截断，系统提示原样 |
| 128k，系统提示 40k token（kept 吃满目标） | 摘要 max_tokens = **8000**（旧版 512） |
| 256k，系统提示 72k token | 摘要 max_tokens = **8192** |
| 阶梯重试 | 512→1024→2048→4096 成功；耗尽时错误含完整重试链与最终值 |
| 400 减半 | 16000→8000→4000 成功，缓存 `{('url','model'): 4000}` |
| assistant 大 tool_calls + reasoning | 参数 120k→9.2k 字符、reasoning 截断，call_id 与 tool 消息仍配对 |
| 失败诊断 | `last_error` 含目标/保留/预算 |
