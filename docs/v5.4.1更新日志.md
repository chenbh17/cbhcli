## 一、修复：管理页面修改主密码不生效（用户报告）

> 用户反馈：「在管理页面设置里修改主密码后，还是原来的密码生效（新密码登不进去）」

### 复现与根因

- **复现**（端到端）：`CBHCLI_ADMIN_MASTER_KEY=<旧密码> cbhcli-admin` 启动 →
  管理页面改密码 → 新密码登录 **401**、旧密码仍 **200**（重启后依旧）
- **根因**：`verify_master_key()` 中环境变量**无条件最高优先**——改密码只写
  `admin.json`，但只要启动配置里有 `CBHCLI_ADMIN_MASTER_KEY`（crontab/systemd 常见），
  校验永远走环境变量 → 新密码永远不生效、旧密码永远可用

### 修复：引入"显式修改"语义（`admin.json` 新增 `key_source` 字段）

| 优先级 | 来源 | 说明 |
|--------|------|------|
| ① | admin.json `key_source="explicit"` | 管理页面 / `--set-password` 修改过的密码，**最高优先且立即生效**（管理页面/新会话登录均使用新密码） |
| ② | 环境变量 `CBHCLI_ADMIN_MASTER_KEY` | 未修改过时的部署凭据（改环境变量即改密码，行为不变） |
| ③ | admin.json `key_source="bootstrap"` | 首次启动引导写入 |
| ④ | 内置默认口令（hash） | 兜底 |

**兼容性**：旧 `admin.json`（无 `key_source` 字段）自动按"引导"语义处理，**无需数据迁移**。

### 配套改动

- 管理页面改密码：返回明确文案；检测到启动配置中存在 `CBHCLI_ADMIN_MASTER_KEY` 时
  返回 **warning**（说明该环境变量已不再作为凭据、服务已自动同步、启动配置无需修改）
- 管理页面改密码后**吊销其它管理会话**（保留当前）
- 设置页 / 启动 banner / `status` 自检显示实际生效的「主密码校验源」
- README / 帮助文案同步（crontab 说明：改密码后无需修改启动配置——服务自动处理）

## 二、主密码修改自动化（无需任何人工操作）

> 设计目标：**改密码后用新密码登录即可**——不需要改环境变量、不需要改启动配置

- **改密码立即生效**：新主密码写入 admin.json（`key_source=explicit`，优先级最高），
  管理页面/新会话登录立即使用新密码；服务运行中无需重启
- **环境变量自动让位**：
  - 运行中的服务在改密码时**自动同步进程内环境变量**为新密码
  - 外部启动配置（crontab/systemd）中的 `CBHCLI_ADMIN_MASTER_KEY` **无需修改**——
    它是启动方定义的，改密码后该旧值不再作为凭据；服务重启时仅打印一条提示，
    仍以已修改的主密码继续启动（不影响使用）
- `--set-password` 修改主密码**必须验证当前密码**（无任何跳过校验的通道）
- 无命令级"重置"通道（忘记主密码时由服务器管理员删除 `admin.json` 中
  `master_key_hash`/`master_key_salt`/`key_source` 三个字段后重启，回落环境变量/内置默认；
  需服务器文件权限，即最高权限边界）

## 三、服务设置全项排查（同步修复 8 项）

| # | 问题 | 修复 |
|---|------|------|
| 1 | `PUT /admin/api/settings` **无任何校验**（可写入 `strict_grace_minutes=-5`、`snapshot_max_mb="abc"` 等 → 客户端 `float()` 崩溃 / 所有快照被跳过） | 服务端新增 `SETTINGS_SPEC` 校验（类型+范围），非法值返回 **400**；`get_settings` 对历史脏数据回落默认值 |
| 2 | `auto_renew` 是**死设置**（`_policy()` 读取但不在 `DEFAULT_SETTINGS` 白名单，前端无入口，永远 True） | 加入默认设置 + 校验规则 + 设置页开关（关闭后到期需人工续期） |
| 3 | `report_level=summary` 是**死设置**（服务端下发，客户端从不消费——用户以为"摘要上报"生效了，实际全量） | 客户端 reporter 落地：summary 跳过 `stream_chunk`（实时流式内容），保留结构化审计事件；30s 缓存避免高频读文件 |
| 4 | 用户「续期为永久」**不写回用户记录**（`update_user` 通用 `v is None 跳过` 吞掉永久值）→ 本次续期永久、**下次登录又恢复旧天数** | `update_user` 对 `token_ttl_days` 特判（支持 None=永久）+ `_normalize_user_ttl` 规范化（forever/null/空/≤0 → 永久；非法值拒绝） |
| 5 | 续期弹窗：**永久用户默认显示 30 天**（不改直接确认就把永久改成 30 天） | 默认显示「永久（不设置有效期）」 |
| 6 | 管理登录限流把**成功登录也计入**（5 次/分钟后被限流，改完密码重新登录易被误伤） | 仅统计失败尝试；成功登录清空计数 |
| 7 | 同数据目录多实例（不同端口）退出时 `server.json` **互相删除** | `_clear_server_json` 校验 pid 后再清理 |
| 8 | `report_api` 快照上限 `float()` 对脏值抛异常（500） | try 兜底 + 非正数回落默认 10MB |
| 9 | `kill`（SIGTERM）/Ctrl+C 停止服务时 `server.json` **残留**（uvicorn ≥0.30 优雅关闭后会重新 raise 信号终止进程，跳过 `run_admin` 的 finally/atexit）→ `status` 自检误报"残留信息" | FastAPI **shutdown 钩子**兜底清理（优雅关闭时先清理运行信息再退出） |

**周边加固**：客户端 `guard.py`（strict 模式宽限读取）与 `reporter.py`（快照上限读取）
对 policy 脏值加防御；设置页输入范围提示同步（grace 0~10080 / ttl 1~3650 / snapshot 1~1024）。

## 四、审计日志时间格式修复（用户反馈）

- **问题**：审计日志页「事件日志」的时间列只显示 `HH:MM:SS`（`fmtClock`），
  与「登录记录」的 `YYYY-MM-DD HH:MM:SS`（`fmtAbs`）不一致，跨天事件难以辨认
- **修复**：事件日志时间列改用 `fmtAbs`（**日期 时间**），与登录记录格式完全一致
- 仪表盘"实时活动流"保持紧凑时钟格式（卡片列表，完整时间仍在 title 提示中）

### 7.1 状态栏技能过多时路径等信息被裁掉（`core/input_box.py`）

**根因**：`bottom_toolbar` 不换行（prompt_toolkit 直接裁掉右侧），技能条目多时

**修复**：状态栏按"信息块"自适应分行（块内不拆分、放不下则换行），单块超宽时截断：
- 技能等逗号列表：保留头部完整项名 + `,…`（如 `data-analysis,code-review,…`）
- 路径等普通值：中间省略（保留头尾，如 `~/projects/…/final-target`）
- 终端足够宽时保持原有单行显示（行为不变）；修复后路径始终可见

**验证**：
- 布局单元测试 23 项（宽度 45/60/80/100/120 各场景：每行不超宽、路径/技能均可见）；
- 真实 pty 渲染（宽度 80/120/55 + 宽度切换）：多行 toolbar 正常显示、与 `resize_fix` 补丁共存；
