# v5.1.8 更新日志

## 上下文压缩失败修复（max_tokens 超限 + 静默失败）

### 问题现象
- 用户执行 `/comp` 压缩上下文，**一秒不到就"完成"**，快得反常
- 实际压缩**根本没有成功**：压缩后的"历史对话摘要"开头是一段错误信息
  `[压缩失败: API请求失败: 400 - ... "Range of max_tokens should be [1, 131072]" ...]`
- 即上下文没被压缩，反而被塞进一段失败提示，**污染了上下文**，且用户毫无感知

### 根因分析
这是 v5.1.6 引入"摘要 max_tokens 按预算限制"时埋下的两个叠加缺陷：

1. **max_tokens 超限（400 错误）**：
   - 摘要预算 `summary_budget = 压缩目标(窗口30%) − 保留部分token`
   - 当模型 `context_limit` 很大时（如 qwen3.8-max / deepseek / mimo = 1000000），
     `compression_target = 1000000 × 0.3 = 300000`，`summary_budget` 算出 20+ 万
   - 这个值被原样当作 `max_tokens` 传给摘要 API，但 **API 的 max_tokens 上限只有 131072**
     → 直接 400 `invalid_parameter_error`
   - 本质：内部计算的预算值与外部 API 的 max_tokens 上限之间**缺少封顶/校验闸门**

2. **静默失败（最危险）**：
   - `_generate_summary` 捕获异常后**不抛出，而是返回 `[压缩失败: ...]` 占位文本**
   - `compress()` 把这段占位文本当成正常摘要，继续 `_save_backup` + `replace_messages`
   - 结果：失败被伪装成"压缩成功"，上下文被污染，用户完全被蒙在鼓里
   - 这正是"一秒不到"的原因——API 秒回 400，代码把失败文本当摘要塞了进去

### 修复方案
**① 给摘要 max_tokens 封顶（治本，消除 400）**
- `core/constants.py` 新增 `SUMMARY_MAX_TOKENS = 65536`（64k）
- `_generate_summary` 实际传参 `max_tokens = min(summary_budget, SUMMARY_MAX_TOKENS)`
- 64k 对结构化摘要（9 章节）绰绰有余，且兼容主流 API 的输出上限

**② 失败不再静默（治本，杜绝污染）**
- `_generate_summary` 失败时**直接抛出异常**（删除 `[压缩失败...]` 占位文本返回）
- `compress()` 用 try/except 捕获摘要生成异常：失败时**不替换会话消息**（保持原样）、
  记录 `self.last_error`、返回 `False`——失败的压缩绝不污染上下文
- `ContextCompressor.__init__` 新增 `self.last_error`（成功时重置为 None）

**③ 失败原因可见（补可观测性）**
各调用点在压缩失败时读取 `compressor.last_error` 展示具体原因：
- CLI `/comp`（session_cmd.py）：区分"压缩失败: {原因}"和"无需压缩"
- CLI 自动压缩（app.py / ai_handler.py）：失败时打印具体原因
- Web（server.py 2 处）：ReAct 自动压缩的 `compress_failed` SSE 事件 + 手动压缩 API
  返回值均携带失败原因

### 验证结果
| 场景 | 结果 |
|------|------|
| 大预算（target=300000）封顶，不再报 400 | ✅ 实际 max_tokens=65536，压缩成功 |
| 摘要生成失败 → 返回 False | ✅ 消息保持原样，无占位文本污染，last_error 已记录 |
| 源码移除 `[压缩失败: {str(e)}]` 占位文本 | ✅ 已移除 |

### 经验教训
1. **静默失败比崩溃更危险**：异常被包装成"正常结果"（占位文本），系统假装成功。
   错误处理绝不能把异常变成"假成功"。
2. **内部计算值传给外部 API 前必须校验/封顶**：不同 API 的 max_tokens 上限不同，
   不能假设内部预算值合法。
3. **新功能要测边界场景**：v5.1.6 只测了常规窗口，没测大 context_limit 模型，
   导致高频必现回归。
4. **失败必须有反馈**：压缩失败无任何提示，靠用户"觉得太快"的直觉才发现。
   可观测性是兜底防线。

## edit 工具 _char_escape_variants 组合爆炸修复

### 问题现象
- edit 工具调用长时间无响应（永久卡死），工具调用显示截断在 `new_str` 中间，无任何输出
- 触发条件：old_str 中包含较多中文全角标点（`，：（）；` 等）+ Unicode 特殊符号（`①②≠` 等）

### 根因分析
`file_edit.py` 的 `_char_escape_variants()` 函数用于 Unicode 转义宽容匹配（v5.1.5 引入），
生成"实际符号 -> 字面转义序列"的组合变体。每个候选符号有 3 种状态（原样/大写转义/小写转义），
组合数为 `4^N`（N = 候选符号数，按 2 位 bit 编码遍历 `1 ~ 2^(2N)-1`）。

两个叠加缺陷导致组合爆炸：

1. **候选筛选条件不够**（第 78 行）：
   - 排除了 CJK 文字（0x4E00-9FFF）和 CJK 标点（0x3000-303F）
   - 但**没排除全角 ASCII 变体**（0xFF00-FFEF），即 `，`（U+FF0C）、`：`（U+FF1A）、
     `（`（U+FF08）、`）`（U+FF09）、`；`（U+FF1B）等全角标点全被选为候选符号
   - 这些全角标点在中文文本中极为常见，绝不会以 `，` 字面转义序列出现在文件中，
     选它们为候选毫无意义

2. **无组合数上限**：
   - 实测一个 259 字符的 old_str（含中文标点+Unicode 符号）选出 **N=19** 个候选符号
   - 循环次数 = 4^19 - 1 = **274,877,906,943**（约 2750 亿次）
   - 每次循环还要 `list(s)` + 字符串拼接，实际执行时间为天文数字 -> 永久卡死

### 修复方案
**① 排除全角 ASCII 变体（治本，减少候选数）**
- 候选筛选条件增加 `and not (0xFF00 <= o <= 0xFFEF)`
- 全角 ASCII 标点（0xFF00-FFEF）是 ASCII 字符的全角形式，不会以字面 Unicode 转义序列
  出现在文件中，排除它们语义正确
- 修复后同一 old_str 候选数从 19 降至 5（只剩 `①②≠→` 等真正的特殊符号）

**② 候选数上限兜底（防护，防极端场景）**
- `if len(idxs) > 10: return []` -- 候选超过 10 个时直接跳过变体生成
- 4^10 = 1,048,576（约 100 万），可接受；4^15 = 10 亿，开始卡顿；4^19 = 2750 亿，永久卡死
- 双保险：即使将来出现新的 Unicode 符号范围漏网，也不会卡死

### 修复效果
| | 修复前 | 修复后 |
|---|---|---|
| 候选符号数 N | 19（含全角标点 `，：（）；`） | 5（只剩 `①②≠→`） |
| 循环次数 | 4^19 = **2750 亿**（永久卡死） | 4^5 = **1024**（瞬间完成） |

### 改动文件（1 个）
| 文件 | 改动 |
|------|------|
| `tools/file_edit.py` | `_char_escape_variants` 候选筛选增加全角 ASCII 排除 + 候选数上限 10 |

### 经验教训
1. **组合算法必须有规模上限**：`4^N` 指数增长极快，N=15 就 10 亿，N=19 就 2750 亿。
   任何遍历 `2^k` 或 `4^k` 的代码都必须设 N 上限或提前剪枝。
2. **候选筛选要区分"需要转义匹配的符号"和"常见的中文标点"**：全角 ASCII 变体
   （0xFF00-FFEF）是中文文本的日常标点，不是 LLM 转义链路会破坏的"特殊符号"，
   不应参与 Unicode 转义变体生成。
3. **v5.1.5 引入宽容匹配时只测了短 old_str（1~3 个候选）**，注释写"候选符号数通常很小
   （1~3 个）"，但没考虑中文长文本场景，全角标点轻松到 10+ 个。

## 流式响应中 Ctrl+C 无法中断修复（SIGINT 被 chromadb Rust 内核忽略）

### 问题现象
- 在终端（尤其 JupyterLab 终端）运行 cbhcli 问答时，AI 流式输出过程中按 **Ctrl+C 只显示
  `^C` 符号，无法中断**，响应继续输出到底；Esc 也失效。
- 空闲提示符下 Ctrl+C 正常，仅流式期间失效。

### 根因分析
1. **终端 SIGINT 送达正常**（`trap ... INT` 能捕获、`sleep` 能被中断），排除终端/PTY 问题。
2. 读 `/proc/<cbhcli_pid>/status` 信号掩码发现关键差异：
   - **空闲 prompt**：`SigCgt` 含 bit2（SIGINT 被 Python 捕获）→ Ctrl+C 正常
   - **流式期间**：`SigIgn` 含 bit2（**SIGINT 被忽略**）→ KeyboardInterrupt 永不触发
3. 流式期间进程内出现 **`tokio-rt-worker` ×24 + `sqlx-sqlite-wor` ×3** 线程——这是
   **chromadb 的 Rust/Tokio 内核**（向量库）。该 Rust 运行时启动时把 SIGINT 置为
   `SIG_IGN`，且信号 disposition 是进程级的，导致主线程流式读取期间 Ctrl+C 失效。
4. cbhcli 自身源码无任何 `signal.signal` 调用，tiktoken/requests 单独使用也不设置，
   隔离测试确认是 chromadb Rust 内核所致。

### 修复方案
`core/model.py`：
- 新增模块级函数 `_ensure_sigint_handler()`：若 `signal.getsignal(SIGINT) is SIG_IGN`，
  则重置为 `signal.default_int_handler`（恢复 Ctrl+C 抛 KeyboardInterrupt）。
- 在 `chat_stream()` 的阻塞读取 `for line in response.iter_lines():` **之前**调用它，
  确保每次流式读取前 SIGINT 可中断（对抗 Rust 运行时设置的 SIG_IGN）。

### 验证结果
| 场景 | 结果 |
|------|------|
| JupyterLab 终端流式中按 Ctrl+C | ✅ 出现「操作被中断。输入 'quit' 退出。」并回到 `❯` 提示符 |
| 空闲提示符 Ctrl+C | ✅ 不受影响 |

| 文件 | 改动 |
|------|------|
| `core/model.py` | `import signal` + 新增 `_ensure_sigint_handler()` + `chat_stream` 阻塞读取前调用 |

### 经验教训
1. **Ctrl+C 失效先查信号掩码**：`/proc/<pid>/status` 的 `SigIgn`/`SigCgt`（bit2=SIGINT）
   能直接定位是"被忽略"还是"未送达"。
2. **带 Rust/C 运行时的依赖（chromadb 等）可能改进程级信号 disposition**：Tokio 内核
   会把 SIGINT 置 SIG_IGN，Python 侧需在关键阻塞点前主动恢复默认处理器。
3. **现象在装 cbhcli-jupyter 插件后出现，但根因与插件无关**：终端 cbhcli 是独立进程，
   真正触发点是 chromadb Rust 内核（排查时勿被表象误导）。
