## 1. 新建会话第一轮运行中，切走再点回报"会话不存在"

**复现**：新建会话 A 发第一条消息（第一轮运行中）→ 点"新建会话"创建
B → 点侧边栏会话 A → toast 报"会话不存在"（A 明明显示"● 运行中"）。
第一轮结束后再操作则完全正常。

### 根因

`chat_load` 内存会话复用分支的逻辑漏洞（`cbhcli_pkg/web/server.py`）：

```python
fname = _find_history_file_by_id(agent_name, session_id)   # 磁盘找历史文件
if fname and not _live_session_stale_vs_disk(live, fname):  # ← 漏洞
    ...复用内存会话...
```

复用条件**隐含要求磁盘上存在该 id 的历史文件**。而新建会话第一轮
运行中，每轮对话自动保存（autosave，v5.2.6）尚未执行（每轮结束才落盘）
→ 磁盘无文件 → `_find_history_file_by_id` 返回 None → 复用分支被
跳过 → `filename` 为空 → 按 id 的 glob 兜底也找不到文件 → 404。

第一轮结束后已落盘、fname 非空 → 复用正常——这正是"只有第一轮出
问题"的原因。侧边栏"● 运行中"徽标来自内存注册表（`_sessions_by_id`），
于是出现"显示运行中却说不存在"的自相矛盾。

### 修复

磁盘无文件（`fname is None`）时，内存副本是**唯一真相来源**（不存在
外部进程更新磁盘导致的过期问题），直接复用：

```python
if fname is None or not _live_session_stale_vs_disk(live, fname):
```

已落盘的会话仍走原有新鲜度校验（CLI 等外部进程更新磁盘时从磁盘重载）。

## 2. 连锁修复：运行中会话导出消息双份渲染

404 修复后暴露的次生问题：`_live_export_limit` 旧写法

```python
return getattr(cs, "run_start_msg_count", 0) or None   # ← 漏洞
```

在第一轮运行时（`run_start_msg_count=0`）把"截断到 0 条"错误变成
"不截断"——全量导出含本轮 user 消息，与 WebSocket 回放的 `run_start`
事件（`renderIncomingUserMessage`）双份渲染 user 气泡。

修复：0 也是有效截断（`max(0, int(...))`），会话运行中导出消息一律
截断到本次运行开始处，当前运行的内容由事件日志回放渲染（保证多浏览
器一致，v5.2.9 既有语义）。

> 通用教训：`x or None` 把合法值 0 吞成 None 是隐蔽的逻辑漏洞——
> "空/零值也有语义"的场景必须显式判空（`is None`），不能用 or 短路。

## 验证

- 独立单测 9 项全过：本 bug 场景 + 4 个回归场景（已落盘复用 / 内存
  过期磁盘重载 / 重启按 id 找回 / 真不存在仍 404）+ 导出截断语义
- 反向验证：临时还原修复前代码，测试精确复现 404（证明测试有效）
- 端到端（临时 agent + 纯 API 零 LLM）：新建会话 B → 新建 C →
  `load(session_id=B)` 返回 200 且正确复用（修复前 404）

## 3. 压缩上下文报错 NoneType has no attribute "strip"（qwen3 等思考模型）

**复现**：模型配置为 qwen3.8-27b（思考模式默认开启），上下文压缩时失败，
错误信息为 `'NoneType' object has no attribute 'strip'`。

### 根因

`LLMClient.chat()`（`cbhcli_pkg/core/model.py`）直接链式取值并 strip：

```python
return result["choices"][0]["message"]["content"].strip()
```

思考模型（qwen3 系列）在思考阶段耗尽 `max_tokens` 时，API 返回
`content=null`（内容全在 `reasoning_content`，`finish_reason=length`），
对 None 调 `.strip()` 即抛 `AttributeError`。异常被 `compress()` 捕获后
写入 `last_error` 展示，用户看到的就是这句 NoneType 报错——既崩溃又无
诊断价值。压缩摘要请求走 `skip_thinking=True`（不带 thinking 参数，
v5.2.4 对不支持 disabled 的 API 的兼容做法），qwen3 部署端默认思考开启，
该参数无法关闭它，思考 token 计入摘要预算 → 预算被烧光 → content=null。

### 修复（三层）

1. **安全提取**：`content`/`reasoning_content`/`finish_reason` 均安全
   取值（None→空串），不再链式崩；
2. **一次翻倍重试**：`content` 空 + `finish_reason=length` + 请求带
   `max_tokens` → 说明截断发生在思考阶段，`max_tokens` 翻倍（封顶
   `SUMMARY_MAX_TOKENS`=64k）重试一次——多数场景思考完成后能正常产出
   正文，压缩直接成功；
3. **诊断性异常**：仍为空则抛出可读错误（含 finish_reason、思考内容
   字符数、max_tokens 值、"建议调大 max_tokens 配置或关闭思考模式"），
   由 `compress()` 优雅捕获 → 会话保持原样不污染，`last_error` 可指导
   用户自行修复。

非流式 `chat()` 仅两处调用方：压缩摘要（compressor）、图片识别 fallback
（image 工具），均有异常捕获，行为兼容。

**验证**：mock 单测 9 项全过（正常返回 / 翻倍重试成功且预算正确 /
重试仍空抛诊断 / stop+空不重试 / 空串 / 封顶不重试 / compressor 端到端
失败优雅且 last_error 可读）。

> 教训：API 响应字段（content）**任何时刻都可能是 null**，链式取值后
> 直接调用字符串方法 = 崩溃；失败信息必须可诊断（为什么空 + 怎么办），
> 而不是裸异常文本。
