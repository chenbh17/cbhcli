# CBHCLI v5.5.0 更新日志（全屏 TUI 重构）

发布日期：2026-10-25
类型：**界面架构重构**（CLI 默认界面切换为全屏 TUI）

---

## 一、为什么重写

旧 CLI 界面（内联模式）把输入框、状态栏、思考窗口画在**主屏**上，靠"相对擦除"更新：

```
画 N 行 → 下次 \033[NA 上移 → \033[J 擦干净 → 重画
```

这套做法隐含三个必须成立的前提：**上次行数不变、区域顶行不变、光标偏移不变**。
终端 resize 会 reflow（重排/滚屏/光标跟随策略因终端而异），三个前提同时失效，于是：

- 思考窗口在窗口变窄时**大量重复换行**；
- 输入框在 resize 后**擦除错位 / 残留 ❯**；
- Jupyter 终端刷新页面（terminmado 重放字节）后，相对转义序列作用在错误的屏幕状态上 → **内容重复**。

此前 `resize_fix.py`（609 行）已迭代四轮，本质是在**逆向猜测不同终端的 reflow 行为**（VTE 光标跟随内容 / xterm.js 光标不跟随），没有普适正确解。

v5.5.0 换掉所有权：**全屏（alternate screen）模式下整屏归应用所有，用绝对坐标差分重绘**，不再有"估算行数擦除"。resize 只是布局重算；页面刷新重放的是幂等的绝对定位序列。

## 二、界面变化（用户可见）

### 1. 三层布局

```
┌ 主区（可滚动历史）──────────────────────────────┐
│ 用户回显 / AI 回复 / 工具卡片 / 思考窗口 / 子Agent │
├ 输入区（固定底部，补全菜单预留 8 行）─────────────┤
│ ❯ 输入…                                          │
├ 状态栏（模型/上下文条/Agent/链条/技能/路径）───────┤
└──────────────────────────────────────────────────┘
```

- 主区滚动：**鼠标滚轮**（3 行/格）、`PgUp` / `PgDn`（90% 屏高）、`Ctrl+Home` / `Ctrl+End`；上翻后**暂停跟随**，`Ctrl+End` 恢复；
- 历史缓冲上限 5000 行；
- 输入区最多占屏幕 1/3，超出内部滚动，状态栏永不被挤掉；
- `Ctrl+L` 清空主区视图（会话/transcript 不受影响）。

### 2. 思考窗口 / spinner / 子 Agent 状态板

- 思考窗口：`💭 思考中... Ns` + 最近 8 行（终端矮时收缩），不再上移擦除；
- spinner：主区底部固定活动行，80ms 刷新、结束原地变 `● 完成/● 失败`；
- 长命令（`/embedding index`、`/kb reindex`、`/comp`、`/mcp add|refresh`）：超过 300ms 才出现活动行，结束移除；
- 并行子 Agent 状态板：主区末尾临时块，结束后清除。

### 3. 状态栏新增上下文占用条

```
上下文: ██████░░░░ 79,872/1,000,000 (7.9%)
```

- 10 格 `█/░`；<60% 绿 / 60%~80% 黄 / ≥80% 红（压缩触发线）；
- 常驻可见（含请求进行中），500ms 节流精确重算（`TokenCounter` 无缓存，禁止每帧全量分词）；
- 窄终端按 10→6→4→无条 降级。

### 4. 应用内模态（不再 SUSPEND）

命令向导、工具确认 `[Y/n/all/always]`、`ask_user`、`/login` 密钥，全部改为**全屏内的提示行 + 单行输入**：

- 菜单/预览就在上方，**作答时可见**；
- `Esc` / `Ctrl+C` 取消；
- 密码模式**不显示任何字符**（连 `*` 都没有）；
- 输入区草稿保留，模态结束后回来。

### 5. Ctrl+C 五级状态机

| 优先级 | 状态 | 行为 |
|---|---|---|
| 1 | 模态打开 | 取消模态（等价 Esc） |
| 2 | 工具执行中 | 调 `interrupt()`：terminal → `killpg`；process → 停监控（任务继续） |
| 3 | AI 请求中 | **协作式中止**（每个流式 chunk / 每轮 ReAct 检查），补全 tool 消息、保存会话、保留草稿 |
| 4 | 命令执行中 | 取消命令（尽力） |
| 5 | 空闲 | 清空输入 + `操作被中断` 提示 |

### 6. 退出与 transcript

- 退出时先把最近 200 行（带颜色）回填到主屏，再打印 `再见!`；超过 200 行时页脚给出 transcript 路径；
- transcript：`~/.cbhcli/agents/<agent>/history/transcripts/<日期>_<会话ID>.log`
  - 只写**已提交的普通行**（纯文本、无 ANSI）；思考窗口/spinner/活动行不写入；
  - 目录 0700 / 文件 0600；64 行或 500ms flush；`/new` 自动换文件；失败静默；
- `--no-save`：不写 transcript，也不做退出 dump。

### 7. 键位

- 项目自定义：`Enter` 提交、`Ctrl+J` / `Alt+Enter` 换行、`Ctrl+R` 详细/简洁、`Shift+Tab` 权限模式（YOLO 二次确认）
- PromptSession 同款：`Ctrl+C`（状态机）、`Ctrl+D`（空输入退出）、`Ctrl+Z` 挂起、`Tab` 补全、`↑↓` 历史/移行
- prompt_toolkit 默认编辑键全部保留：`Ctrl+A/E/B/F/K/U/W/Y/T/P/N/G`、`Alt+B/F/D/Backspace`、`Home/End`、`Ctrl+←/→`、`Shift+方向键` 选区、`Ctrl+_` 撤销
- 新增：`PgUp/PgDn` 翻页、`Ctrl+Home/End` 到顶/到底、`Ctrl+L` 清屏、**鼠标滚轮滚动历史**、**`F2` 切换鼠标捕获**（选中文本用 Shift+拖动）

## 五、已知限制

1. **`python` 工具无法强杀**：同进程 `exec`（保留跨调用变量共享），Ctrl+C 会立即反馈并阻止进入下一轮，但当前代码要等自然返回；
2. **256 色的 232/254/255** 受 prompt_toolkit 量化表 off-by-one 影响，单通道 Δ≤17/255（肉眼不可见）；其余 253 个索引精确；
3. 鼠标捕获默认开启（滚轮需要它）：选中文本请 **按住 Shift 再拖动**（终端原生选中）；`F2` 关闭捕获后可**直接拖动选中**，滚动改用 `PgUp/PgDn`；
4. transcript 不自动轮转/清理，长期使用需自行归档；
5. 命令执行中的 Ctrl+C 为协作式（无轮询点的 C 调用需等返回）。

## 八、补充修复（2026-10-25，用户实测反馈）

### 1. 思考窗在终端变窄后重复换行（已修）

**现象**：全屏下把终端拖窄，思考内容整块重复出现；越拖越多。

**根因**：`ThinkingDisplay` 里有一段**内联时代**的防御逻辑：

```python
if current_width < self._region_width:
    self._region_lines = 0        # 放弃擦除
    self._region_width = current_width
    self._draw()                  # 直接在下方重画
```

内联模式下这是对的：旧窗口可能已被终端 reflow，"按旧行数上移擦除"会误删上方内容，所以留作一次性快照。
但**全屏模式的 `erase_up(n)` 移动的是逻辑行**——屏幕宽度变化不改变逻辑行数，擦除永远安全。
于是每次收窄都留下"上一整个窗口"，滚动窗口又只含最后 8 行 → 重叠部分看起来就是"重复换行"。

**修复**：
- `ScreenSink.logical_erase = True`（能力标记）；
- `ThinkingDisplay._logical_erase()` 读该标记：
  - **全屏**：一律擦除重绘，并按当前宽度重新硬折行（窗口始终 ~8 行）；
  - **legacy**：保持原快照策略（未受本次修改影响）；
- 顺带修好"终端变**宽**后窗口仍按旧窄宽度折行"的问题。

**验证**：`tests/ui/check_think_resize.py`
- 缓冲层：模拟 100→80→60→40→100 反复变宽窄，最终缓冲只有 1 个 `💭` 窗口、17 个 chunk 无重复；
- 物理屏幕层：真实 `Application` 流式思考中 resize（100×30 → 60×14 → 40×10 → 100×30 → 30×12），重放终端输出后可见区域只有 1 个窗口、无重复标记；
- legacy 兜底：确认收窄时仍是快照（不会误擦上方内容）。

### 2. 鼠标滚轮滚动历史（新增）

**背景**：V1 按"不捕获鼠标"设计（保护原生拖动选中），用户实测后要求"滚轮能看历史"。

**实现**：
- `Application(mouse_support=True)` → 发 `?1000h / ?1015h / ?1006h`；
  启动后主动补 `\033[?1003l`（prompt_toolkit 默认会开 any-motion，关掉可避免鼠标移动事件洪水）；
- `_WheelWindow`（主区 + 输入区）拦截 `SCROLL_UP / SCROLL_DOWN` → `_scroll(±3)`，复用既有的"上翻暂停跟随 / 回到底部"逻辑；
- **`F2`** 切换鼠标捕获：关闭后恢复原生拖动选中（滚动用 `PgUp/PgDn`），并在主区打印一行提示。

**取舍说明**：终端协议上**无法只捕获滚轮**——开启鼠标上报后左键必被捕获。
（补充迭代 5 已回退：仍用 **Shift+拖动** 选中；F2 提示改到状态栏。）

**验证**：`tests/ui/check_mouse_wheel.py`（pty 发送 SGR 滚轮事件 + F2，`Screen` 重放断言可见行号变化）。

### 3. 思考过程"窗口总闪"（已修）

**现象**：思考流式输出时，思考窗口高频抖/闪（JupyterLab 浏览器终端尤其明显）。

**根因**（两条叠加）：
1. **每个 chunk 都全量重绘**：模型流式可达几十~上百 chunk/秒，每个 chunk 都"擦掉 9 行 + 重写 9 行"，
   xterm.js 就要重绘 9 行 × 上百次/秒 → 视觉上就是闪；
2. **擦除与重写不是原子的**：`erase_up()` 和紧随的 `write()` 是两次 `feed()`，各自触发一次重绘，
   渲染线程可能插在"已擦除、还没写回"的中间状态画一帧（窗口闪一下）。

**修复**：
- `FullScreenUI.atomic()`（+ `SinkWriter.atomic()` / `ScreenSink.atomic()`）：其内多次 write 不重绘，
  退出时只重绘一次；思考窗口的"擦除 + 重写"整体包进去；
- **重绘节流** `_REDRAW_INTERVAL = 0.12s`：chunk 只累积文本，最多 8 次/秒重绘；尾包由
  daemon `threading.Timer` 兜一次（保证最后一个 chunk 也会显示）；`finish_thinking`/`cleanup` 取消定时器；
- **只对全屏生效**（`logical_erase`）：legacy 内联模式保持"每 chunk 都画"的旧时序，避免 Timer 与旧输出流交错。

**量化**（`/tmp/measure_flicker.py`，40 个 chunk @10ms）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 渲染帧数 | 43 | **7**（降 84%） |
| 终端输出量 | 8305 B | **2300 B**（降 72%） |
| 中间空帧 | 0 | 0 |

### 4. 滚轮在 JupyterLab 终端完全失效（已修，根因在 xterm.js）

**现象**：本地终端滚轮正常，但 JupyterLab 终端（xterm.js）里滚轮毫无反应。

**根因**：为了关掉 prompt_toolkit 自带的 `?1003h`（any-motion，鼠标移动事件洪水），
我们启动后补写了 `?1003l`。**xterm.js 把任何一个鼠标模式的 reset 都实现为
`activeProtocol = "NONE"`**（源码：`case 9: case 1000: case 1002: case 1003: activeProtocol="NONE"`），
于是 `?1003l` 把 `?1000h`（点击/滚轮）一起关掉了 —— 终端不再发任何鼠标事件，
本地终端（xterm/VTE）没这个语义，所以只有 JupyterLab 里坏。

**修复**：`_MOUSE_RESTRICT_SEQ = "\033[?1003l\033[?1000h\033[?1006h"` —— 关 1003 后**立刻重发 1000h + 1006h**；
由 `Application(after_render=...)` 在首次渲染后执行（幂等），任何嵌入方（CLI/tests）都自动生效。
F2 重新开启时也走同一序列。

**诊断入口**：`CBHCLI_FS_DEBUG=1 cbhcli` → 鼠标事件与模式切换写入 `/tmp/cbhcli_fs_debug.log`
（若滚轮仍无效，先看日志里有没有 `mouse MouseEventType.SCROLL_UP`：没有=终端没发事件，有=应用侧问题）。

### 5. F2 提示不再写主区（修复）

**现象**：思考过程中每按一次 F2，思考窗口就整体下移一行。

**根因**：F2 的处理里用 `print()` 把提示写进了**主区**。思考窗口靠"上移 `_region_lines` 行 + 重写"
重绘，主区凭空多一行 → 上移行数不再匹配 → 窗口错位一行（并吞掉一行内容）。

**修复**：提示改由 `FullScreenUI._set_notice()` 写到**状态栏**（3 秒后消失），主区一行不动；
且放在状态栏**最左侧**（状态栏最多 3 行，追加到末尾容易被裁掉）。

**验证**：`tests/ui/check_f2_notice.py`（按 F2 后主区行数 10→10 不变，提示出现在 `❯` 之后的状态栏区域）。

> 说明：本轮曾尝试"应用内鼠标选中（拖动即高亮复制、无需 Shift）"，按用户要求**已回退**：
> 选中仍用终端原生的 **Shift+拖动**，鼠标只负责滚轮。

### 6. 状态栏「运行中」动画（新增）

会话正在执行（AI 请求 / 命令）时，状态栏最左侧显示**旋转的 braille spinner + 运行中**：

```
⠹ 运行中 │ ● 标准 │ 模型: deepseek-flash │ 上下文: █░░░… │ Agent: main │ 路径: …
```

- 帧序列 `⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏`，**100ms/帧**（约 1 秒转一圈），由 daemon 线程驱动，
  只在 `busy=True` 期间运行；`set_busy(False)` / 退出时停止；
- 颜色改用青色（`bold #5fd7ff`），**不再使用黄色圆点 ●**；
- 动画只重绘状态栏（单元格级 diff），主区一行不动，不影响思考窗口；
- 空闲时该标识完全不出现（无残留、无后台线程空转）。

**验证**：`tests/ui/check_running_badge.py`（`set_busy(True)` 时出现且连续采样到 ≥3 个不同帧、
`set_busy(False)` 后消失、主区行数不变）。

### 7. 第二轮输入错位 / 「最前面有一位退格退不掉」（修复）

**现象**（用户实测）：第一轮对话结束后，第二轮输入时输入行文字错位，行首残留一个退格删不掉的字符。

**根因（终端换行 → 整屏滚动）**：
全屏界面把主区/状态栏**写满终端最后一列**时，若最后一格是**宽字符**（CJK/emoji，占 2 列）
或被裁切的宽字符，终端会触发自动换行；换行发生在**最底部（状态栏）**时终端会**整屏上滚 1 行**。
prompt_toolkit 并不知道这次滚动 → 后续所有相对光标操作整体错位 →
输入行被画到偏移的位置，行首留下上一行的残格，而残格不在 Buffer 里，所以**退格删不掉**。

**修复**：
1. **最右预留 1 列**：布局改为 `VSplit([主界面, Window(width=1)])`，任何行都不写终端最后一格
   （宽字符裁切最多溢出到预留列，不会触发终端换行，更不会在最底部滚屏）；
2. 主区折行宽度、滚动上限、输入区高度估算统一按 `cols-1`（输入区再扣提示符 `❯ `）；
3. 输入区高度估算改用 **prompt_toolkit 的宽度口径**（`max(display_width, get_cwidth)`），
   避免 emoji/组合字符被低估 → 行数算少 → 输入框内部错位。

**验证**：新增 `tests/ui/check_input_boundary.py`，用 **pyte**（列精确重放）在 **40 列窄终端** +
中文长行 + 中文状态栏下断言：输入行 `❯ 你好abc`、光标列 9、行号不变；退格 3 次 + `xy` 后
`❯ 你好xy`、光标列 8 —— 全部通过（源码版与已安装版各跑一次）。

### 9. F2 提示触发 `❯ nnihao` 残影（修复：最底部一行的宽字符换行）

**现象**（用户实测）：按 F2 弹出"鼠标开关"提示后，下一轮输入出现 `❯ nnihao`。

**根因**：F2 提示是**前置**到状态栏第一行的，状态栏变长后，被窗口在右边界**裁切**；
若裁切点上正好是**宽字符**（中文/emoji，占 2 列），终端会把它算作"超出剩余列" →
**自动换行**；状态栏在**最后一行** → 换行触发**整屏上滚 1 行** → prompt_toolkit 不知情 →
输入行整体上移/错位，行首留下残格（退格删不掉）。

**修复**：
1. **布局最右预留 2 列**（`VSplit([body, Window(width=2)])`）：任何窗口的最后内容格都在
   `cols-3`，宽字符最多占到 `cols-2`，**永远碰不到最后一列**，因此不可能触发换行/滚屏；
   主区折行、滚动上限、输入区高度估算统一按 `cols-2`；
2. **状态栏按显示宽度截断到 `cols-4`**（`_fit_status_frags`，宽字符安全、逐行处理）：
   即便内容超长也只会被我们自己裁掉，不会落到边界让终端去裁；
3. F2 提示文案缩短（`鼠标: 开（滚轮；Shift+拖动选中）`），减少对状态栏的挤压。

**验证**：新增 `tests/ui/check_status_overflow.py`（pyte 列精确重放，40/80/120 列 ×
长中文状态栏 + F2 提示 + 输入 `nihao`）：断言**每一行最后 2 列都是空白**、输入行
`❯ nihao`、行号不变；源码版与已安装版各跑一次全部通过。

### 13. 上下文压缩"只保留最开始一轮/最近对话全丢"（修复，2026-10-25）

**现象**（用户报告）：很长的上下文压缩后，"好像只保留最开始的一轮对话"，最近的用户请求
全部消失，模型表现得像失忆。

**根因**（用真实备份会话 `history/compressions/*.json` 实测复现）：压缩策略用
**"轮数 × 2 条消息"** 估算保留轮次，但一轮真实对话是
`user → assistant(tool_calls) → tool → assistant(tool_calls) → tool → … → assistant`
（可达十几条消息）。于是：

- `keep_recent=3` 实际只取**最后 6 条消息**，这 6 条通常整段落在某一次工具循环中间
  （**一条 user 都没有**）；
- 再经 `_split_at_boundary` 调整（切点落在 assistant(tool_calls) 时向后跳过所有 tool），
  recent 会被吃成 **4 条 / 2 条 / 甚至 0 条**；
- 压缩结果 = 最早一轮（4~6 条）+ 摘要，**最近的用户请求全部进了摘要**。

实测（1245 条消息的会话）：旧逻辑 `keep_recent=3 → recent=4 条、user=0`；
`keep_recent=1 → recent=0 条`。

**修复**：
1. 新增 `_turn_starts()` / `_select_turns()`：**按 user 消息边界切分"轮"**，`recent`
   永远是"最后 N 轮用户请求 + 其完整工具链"，不可能出现"一条 user 都没有"；
2. 保留预算不足时**优先牺牲最早轮**（其内容已进入摘要），**保住最近对话**；
3. 压缩目标自适应：目标不能小于「系统提示 + 摘要下限 + 最小保留」。实测某会话
   system≈56k tokens 而 target=窗口30%≈38k，旧逻辑永远判"超目标"→ 把保留轮压到
   只剩 1 条工具消息。新逻辑按 `system + summary_min + min_keep` 抬高目标
   （并限制 ≤ 窗口 70%，不接近 80% 触发点）；
4. 保留消息的 `reasoning_content` 直接丢弃（思考过程对续任务价值最低、占用最高）；
5. 单条截断下限 400→200 字符（tool_calls 200→100），避免"条数多 → 整体超预算 → 整轮被降级"。

**验证**（真实会话 + 合成会话）：
- 1245 条消息的真实会话：`898,565 → 73,211 tokens`（57.2% 窗口），
  **保留最近 3 轮用户请求**，OAI 消息序列（tool_calls 配对 / system 位置）校验通过；
- 合成 10 轮 / 20 轮会话：保留「最早 2 轮 + 最近 3 轮」用户请求；
- 压缩失败/变小检测等防御逻辑保持不变（绝不把失败伪装成压缩成功）。

### 14. 工具代码预览在窄终端下左右错位（修复，2026-10-25）

**现象**（用户报告）：`write` / `python` / `edit` 的代码预览渲染错位——edit 差异预览
"右侧绿色内容换行跑到左边"，左右红绿对不上。窗口越窄越明显。

**根因**：全屏 TUI 主区文字宽度 = **终端列数 − 2**（最右 2 列为防宽字符触发自动换行
而预留），但预览用 `Console(width=_term_width())` 按**终端满宽**绘制 → 最右 1~2 列
被主区的折行逻辑折到**下一行最左侧**（终端折行从行首开始，不是从单元格起始列），
于是绿色单元格的尾部内容出现在左侧，红绿错位。

**修复**：
1. `FullScreenUI.text_width()`：暴露主区可用文字宽度（`列数 − 2`）；
2. `tool_executor._render_width()`：全屏时取 `text_width() − 1`（rich 用 cell_len、
   主区用 display_width，字素簇宽度可能有细微差异，留 1 列余量），非全屏回退终端宽度；
3. `_render_edit_preview()` / `_render_code_preview()` 的 Console 宽度统一改用它。

**验证**：新增 `tests/ui/check_preview_width.py`（假 UI 宽度 60/80/120 列，长中文行 +
超长代码行）：断言 edit 差异预览与代码预览**每一行显示宽度 ≤ 主区宽度**（不会被主区
再折行），三种宽度全部通过。

### 15. 选中文本后"鼠标一动就消失"（选区保护，2026-10-25）

**现象**（用户报告）：用 Shift+拖动选中主区文字后，鼠标稍微动一下选区就没了。

**原因**：终端在**收到应用输出**时会刷新缓冲区并清除原生选区；而全屏 UI 在以下时机
都会产生重绘输出——鼠标按下/释放（prompt_toolkit 会 invalidate）、每轮结束的输入区修格、
状态栏「运行中」动画（10 帧/秒）、思考窗滚动刷新（0.12s 一次）。于是"刚选好就被冲掉"。

**修复（重绘静默期）**：
1. `_on_mouse_activity()` 记录鼠标事件时间与左键按下状态（滚轮除外——滚轮必须跟手）；
2. `_mouse_quiet_delay()` / `_defer_invalidate()`：鼠标事件后 **0.6 秒内不重绘**
   （内容照常进 Screen，只是推迟画），按住左键（可能在拖选）时持续静默，
   但最多 3 秒（避免流式输出卡死）；
3. 静默期结束后统一补一次重绘（`invalidate()`、`_schedule_full_repaint()` 都走同一入口）；
4. 补齐关闭 `?1015`（urxvt 鼠标编码），只保留 `?1000h`（点击/滚轮）+ `?1006h`（SGR）。

> 说明：Shift+拖动本身由终端处理（不上报应用），应用无法知道"用户正在选中"，
> 所以采用"鼠标操作后短暂抑制重绘"的保守策略。若在 AI 流式回复过程中选中，
> 选区仍会被后续输出冲掉（终端行为），建议回复结束后再复制。
