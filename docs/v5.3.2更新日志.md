# v5.3.2 更新日志

> 发布日期: 2026-09-12
> 主题: MCP 接入体验增强（引号包裹 header / 名称可省略 / `${ENV}` 占位符展开）

## 背景

接入阿里云百炼等「带认证的远程 MCP 服务」时暴露两个问题：

- `/mcp add srv URL Authorization=Bearer sk-xxx` 按**空白拆分**：`Authorization` 值只剩 `Bearer`，
  `sk-xxx` 作为无 `=` 的 token 被**静默丢弃**（不报错、不提示）→ 401 鉴权失败且无从排查
- `${DASHSCOPE_API_KEY}` 这类环境变量占位符不被展开（全项目无环境变量处理），配置只能写明文 Key

## 一、CLI `/mcp add` 解析增强（`cbhcli_pkg/commands/mcp_cmd.py`）

### 1. 引号感知拆分 `_split_args()`
- 支持单/双引号包裹含空白的 header 值：`Authorization="Bearer sk-xxx"` 或 `"Authorization=Bearer sk-xxx"`
- 引号本身剥离；**引号未配对时回退**到普通空白拆分（保持旧输入行为）
- 不用 shlex：posix 模式会吞掉值中的反斜杠，改变既有输入语义（自定义解析器更保守）

### 2. 名称可省略（URL 自动推导）
- 新增 `_looks_like_url()`（`http://` / `https://` 前缀判定）与 `_derive_server_name()`
- 第一个参数是 URL 时自动推导服务器名：取路径最后一段有意义的片段，跳过 `mcp/sse/stream/api/v1...` 等通用段；
  路径无意义时取主机名最有意义的一段；IP 地址整体使用（`.` 清洗为 `-`）
- 例：`.../TextGenerateImage/mcp` → `TextGenerateImage`；`https://mcp.tianyancha.com/v1` → `tianyancha`
- 自动命名失败（重名等）时附加"可用显式名称"的提示

### 3. `_mcp_add()` 重写
- 用法变为 `/mcp add [名称] <URL> [header名=值 ...]`
- 空 key 跳过（旧版 `=abc` 会解析出空 key header，边界修复）
- 无 `=` 的 token 静默丢弃行为保留（向后兼容）

### 4. 帮助文案（`_mcp_help`）
- 新增「header 写法」说明段：值含空格用引号包裹 / 支持 `${环境变量}` 占位符
- 修正旧示例（`Authorization=Bearer xxx` 实际会丢 token 的错误示范）

## 二、`${ENV}` 占位符展开（`cbhcli_pkg/core/mcp_manager.py`）

### 1. `_expand_env_vars()`（模块级）

### 2. `_client_headers()`（连接层）

- 展开在 **MCPManager 层**统一生效：CLI / Web / 手写 mcp.json / Jupyter 插件全端受益

### 3. 连接失败提示
- 环境变量缺失导致展开失败时，错误信息明确列出缺失的变量名与处理建议

### 4. 同步改造

## 七、同版本迭代追加（第二轮）：CLI 终端 resize 输入框重复 + Web 滚动跟随

> 用户反馈两项体验问题，同版本内修复，不 bump 版本号（前端缓存参数 `?v=` 升为 `5.3.2.1`）

### 1. CLI：终端窗口缩放时输入框重复显示（`cbhcli_pkg/core/resize_fix.py` 重写）

**现象**：拖动/缩放终端窗口后屏幕上残留多份 `❯ 输入内容`（仿真环境实测：拖动 13 次残留 6 份）。

**根因（两层）**：
1. 终端在宽度变化时会**重新折行（reflow）**屏幕内容，使光标的**物理行号**与 prompt_toolkit 记录的
   "渲染区域内相对坐标 `_cursor_pos`"不再对应；
2. prompt_toolkit 的 `erase()` 用**相对移动**擦除——`cursor_backward(_cursor_pos.x)` →
   `cursor_up(_cursor_pos.y)` → `erase_down()`。reflow 后这个相对起点落偏，旧输入框擦不掉，
   而重绘又画一份 ⇒ 每 resize 一次多一份残留（v5.2.x 的 100ms 防抖解决的是"连续 SIGWINCH 踩踏"，
   解决不了 reflow 错位）。

**修复（`install_resize_fix()` 全流程）**：
- 保留 100ms 防抖（拖动中合并 SIGWINCH）；
- 防抖结束后向终端发 **CPR（`\x1b[6n`）**，取终端报告的**绝对光标行号**（天然包含 reflow 后的真实位置），
  推算输入区域首行 `top = row - 上次渲染的光标相对行号(y_old)`；
- **把"绝对定位 `top` 行 + `erase_down()` 清到屏幕末尾"放到渲染函数开头同步执行**
  （包装 `Renderer.render`）。这一步必须与渲染在同一次同步调用里完成：渲染是异步的
  （`invalidate()` → 下一轮事件循环），提前移光标会被期间的 reflow/输出踩掉（实测仍残留 6 份）；
- **绝不主动滚动屏幕、绝不把区域上移**：清除严格从"锚点行"开始（该行往下只会是输入框与
  空白），否则会从历史输出中间开始清——第一版实现为了腾空间先把屏幕向上滚了几行，
  结果用户看到"聊天框往上被擦掉了"（banner 下半截消失）；
- 包装 `layout.container` 把布局**优选高度夹到"锚点行到屏幕底部的可用行数"**：
  `height = max(_min_available_height, last_height, preferred)` 一旦大于可用空间，渲染会用
  `\r\n` 向下移动越过屏幕底部触发滚动（屏幕内容整体上移），夹住 preferred 后渲染恰好填满
  可用空间，不再滚动；
  - **必须"每次渲染"都夹，并锁定 `_min_available_height`**（在 CPR 回调里写回同一数值）。
    只夹"resize 那一次"的话，之后打字时渲染高度又变回去 → 渲染器再次 `\r\n` 向下移动 →
    位置漂移 → **打字时又画出重复的输入框**（用户报"修复后又重新换行了"就是这个）；
  - 夹紧容器**只夹 `preferred`，保留原 `min`/`max`**：把 `max` 一并改大曾导致输入框整块不显示（`❯` 消失）；
- **⚠️ `Vt100_Output.cursor_goto(row, column)` 的行号是 1-based**（实现为
  `"\x1b[%i;%iH" % (row, column)`，行号 0 会被终端当成默认值 1）：传 0-based 会每次 resize
  少定位 1 行 → 输入框逐次上移、`erase_down` 逐步吃掉上方 banner（正是用户报的"聊天框往上擦除"）。
  必须 `cursor_goto(行号+1, 列号+1)`；
- 变宽时用"新宽度 + 当前输入内容"重算光标行号上界并**夹紧**（旧的 `_cursor_pos.y` 可能偏大，
  会让锚点偏上而误删历史；估算偏小最多留一点残影，不会删内容）；
- 内容超屏时（`top < 1`，屏幕上只剩输入区域尾部）钳制到屏幕首行清除（其上方已无可见历史内容，安全）；
- 异常 / 终端不支持 CPR（`cpr_support == NOT_SUPPORTED`）/ CPR 响应超时（0.45s）→ **回退原生 `_on_resize`**，
  保证任何终端下都不会比原来更糟；
- 新增 `CBHCLI_RESIZE_DEBUG=1` 环境变量 → 调试日志写入 `/tmp/cbhcli_resize_debug.log`（默认关闭）。

**验证方式（新建的终端仿真测试台，源码已归档到 `tests/terminal_resize/`）**：`pty` 子进程 + `@xterm/headless` 真实终端模拟
（含 reflow，并在 reflow 后按真实终端语义把光标挪回内容位置）+ 同步点 dump 屏幕。
真实 `cbhcli` 进程输入超长文本（触发折行）后多方向拖动：`❯` 计数 **6 → 1**（无残留）；
16 次连续 resize 全程干净；resize 后继续输入/回车提交/多行输入（Alt+Enter）均正常；

## 八、同版本迭代追加（第三轮）：CLI resize 输入框重复"彻底"修复（CPR 精确清除旧区域）

> 用户实测第二轮修复后仍报"还是不行"（屏幕出现 8 个空 `❯`）。本轮再次重写 `resize_fix.py`，
> 从"CPR 锁定渲染高度 + 回退原生"演进为「**CPR 精确清除旧区域 + 右下角锚点兜底**」。仍不 bump 版本号。

### 1. 第二轮方案为何在用户终端失效
第二轮用 CPR 拿绝对光标行来"锁定渲染高度"，**CPR 不可用时回退原生 `_on_resize`**。
但原生流程是 `renderer.reset()`（清空 `_last_screen`）→ 发 CPR → `invalidate()`，
**reset 后重绘根本不擦除旧区域**，只指望新区域正好覆盖旧区域；一旦 reflow/滚动让位置或高度有偏差就残留。
用户终端 CPR 响应不可靠 → 回退原生 → 每次 resize 残留一个 `❯`。

### 2. 本轮重写：CPR 精确清除（首选）+ 右下角锚点（兜底）
清除必须知道"旧区域真实位置"：**旧区域顶部 = CPR 光标绝对行 − 光标在区域内相对偏移(`_cursor_pos.y`)**。
- `_on_resize` 防抖后**先记录** resize 前的 `_cursor_pos.y` 与 `_last_screen.height`（reset 会清空），
  再 `reset()` + `request_absolute_cursor_position()` 发 CPR，并记一个自增 `seq`；
- patch `Renderer.report_absolute_cursor_row(row)`：响应到达时 `old_top = row − old_cursor_y` →
  清除 `old_top` 到屏幕底部 → 贴底部重绘（`seq` 校验防过期响应误清）；
- **CPR 不支持/超时(0.35s) → 右下角锚点兜底**：`\x1b[999;999H`（钳制到最后一行）→ 上移边距 → **回第 1 列** → `erase_down`；
- 保留"每次渲染夹紧布局 `preferred` 高度"保证高度一致、不再 `\r\n` 向下移动。

### 3. 本轮新发现的关键 bug（全部实测踩出）
1. **`renderer._last_size` 是屏幕尺寸不是区域高度**！用它算区域顶行会得到 1 → 从屏幕第一行重绘覆盖整个 banner；
   区域实际行数在 **`renderer._last_screen.height`**；
2. **清除前必须回第 1 列**（`\x1b[1G`）：`\x1b[999;999H` 把光标放在**最后一列**，此时 `erase_down` 只清"该行光标之后"
   （几乎为空）+ 下方所有行，**残留 `❯` 所在行只被清掉最后一列** → 每 resize 多一个 `❯`（加大边距只是碰巧覆盖，治标不治本）；
3. **渲染限高必须严格 = 区域高度**：限高更大时渲染器"本次高度 > 上次高度"就 `\r\n` 向下移动 → 越底触发滚动 →
   **banner 顶部被推出屏幕**；
4. **静态清除边距无法两全（必须用 CPR 的根本原因）**：启动场景 banner 框底**紧贴**区域上方（多清 1 行就删框底）；
   长对话场景变窄时历史折行、终端滚动、区域**上移 1 行**（少清 1 行就残留 `❯`）。
   同一个 0-based 行，一边是要保护的 banner、一边是要清除的残留，**只有 CPR 拿到真实光标行才能精确区分**。

### 5. 当日修正：恢复"锁定 `_min_available_height`"（用户实报"5 个空 ❯ 逐个下移"真因）

第三轮重写时只夹了布局 `preferred` 高度，**丢了第二轮的"reset 后把 `_min_available_height` 重新锁定为 region_h"这一步**。
`Renderer.render` 内 `height = max(_min_available_height, last_height, preferred)`，而 `reset()` 把 `_min_available_height` 清 0、
CPR 回调 `report_absolute_cursor_row` 又把它设成 `屏幕行数-row+1`；它在两者间波动 → height 忽大忽小 →
`current_height > previous_screen.height` → 渲染器 `\r\n` 向下挪一行 → 每 resize 一次输入框下移一行、旧 ❯ 残留 → 累积成一串 ❯。
xterm.js 因 row 恰好稳定没暴露此 bug，真实终端一缩放就触发。
修复=`_redraw_at` 里 reset 后立刻 `renderer._min_available_height = limit`，并在 `_render_wrapper` 每次渲染夹到 limit（双保险）。
重新打包安装、重启 Web（pid 670054）。
**教训：重写"已验证有效"的修复时必须逐条核对旧版每个关键动作有没有保留，凭记忆重写极易丢步骤；仿真测试全绿 ≠ 真实终端没问题。**

### 6. 当日再修正：重绘必须"原地覆盖"（`top_row = old_top`），不能强行贴底部（用户实报"缩小仍重复"真因）

用户用 `CBHCLI_RESIZE_DEBUG=1` 提供的真实终端日志显示：CPR 正常（SUPPORTED），但**变窄时 `光标行=15、旧区域顶=15，重绘顶却=16`**。
根因 = 我用 `top_row = max(屏幕底-区域高+1, old_top)` 强行把区域"贴底部"重绘：变窄时 reflow 让 ❯ 上移到 15 行，
我却把新区域画到 16 行，中间靠"清除 15 行"擦旧 ❯；而 `reset()` 后 `previous_screen.height=0`，render 必触发
`current_height(9) > 0` → `move_cursor(0, 8)` 用 `\r\n` 向下移动 reserve 空间，真实终端里这一行旧 ❯ 擦不干净
→ 15 行旧 ❯ + 16 行新 ❯ 重复。**修复 = 直接 `top_row = old_top`（CPR 报的光标真实行 = 旧区域顶），让新区域原地覆盖旧区域**，
不再"清除一行 + 下移重绘"；仅当 `old_top + region_h - 1 > 屏幕高` 时才上移贴底。
验证：修复后日志 `旧区域顶 == 重绘顶`（13=13/14=14/15=15/16=16），scene11/12/13+scene1/2 源码版与安装版全绿。
**教训：reflow 后区域会上移，"贴底部"是程序的一厢情愿；既然 CPR 已拿到旧区域真实顶行，就该原地覆盖，任何"清除某行 + 在别处重绘"都给了残留可乘之机。**

## 九、推翻重做：重绘范围严格等于清除范围（用户要求"删掉旧记录、重新做"后）

> 用户实测多轮后仍报"终端缩小换行重复"，并要求删除旧的 resize 踩坑记录、推倒重做。
> 本轮**放弃旧思路**（"清除一段 + 把区域画到另一段"），改为**单一自洽范围**，同时把旧踩坑记录从长期记忆中全部清除。

### 1. 旧版为何反复失败（根因收敛为一句话）

旧版始终在做两件**范围不一致**的事：

```
清除：旧区域顶 ~ 屏幕底部        （N 行）
重绘：固定 9 行的输入框画到别处   （贴底部 / 原地覆盖）
```

两者之间必然留下"**没被重绘覆盖、只能指望清除擦掉**"的行；而 prompt_toolkit 在
`previous_screen` 为空（`reset()` 之后）时**自己还会执行** `move_cursor(0,0) + erase_down`，
再加上 `current_height > previous_screen.height` 触发的 `\r\n` 向下 reserve 空间——
真实终端里只要有一点偏差，那一行的旧 `❯` 就擦不干净 → 重复。

### 2. 新方案（单一自洽范围，`resize_fix.py` 重写）

1. **确定清除起点**
   - CPR 可用：`清除起点 = CPR 光标行 − 区域内偏移`（reflow 后的真实位置）
   - CPR 不可用/超时：屏幕右下角锚点 + 保守边距（`区域高 + 2`，并受屏幕高度一半限制）
2. **清除「起点 ~ 屏幕底部」共 N 行**
3. **把"区域可用高度"锁成同一个 N 行** → 渲染必然从起点逐行向下填满，**不留任何缝隙**
   （这是与旧版的本质区别：不再"清一段、画另一段"）
4. 渲染高度全程锁定：`_min_available_height` 与布局 `preferred` 上限都夹到 N，
   保证 `height = max(...)` 恒定，不触发 `\r\n` 向下移动

### 3. 验证

- 调试日志直接验证范围一致：`清除起点=13 区域行数=12`、`清除起点=12 区域行数=13`
- scene11/12/13（真实 cbhcli）+ scene1/2（裸 prompt_toolkit）源码版与安装版**全绿**
- 重新打包安装（`~/.local`）→ 重启 Web（HTTP 200）
- 长期记忆（memory.md）中 15 处 resize 踩坑记录已按要求全部删除，速查表改为一行功能描述

## 十、第四轮：彻底消除 resize 后 ❯ 残留（双路估算 + 陈旧光标识别）

> 用户实测第三轮后仍报"终端窗口变小后还是会重复换行显示（一串 ❯）"。
> 本轮先在**真实终端仿真台把问题 100% 复现**（非常关键：前几轮都靠推理），
> 再针对性重写清除起点算法。

### 1. 复现（旧代码 100% 复现用户现象）

在 `tests/terminal_resize`（pty + xterm.js 真终端仿真）里：

```
真实 cbhcli（banner + 空输入框），逐列缩小窗口 79→74→68→62→... ：
  旧代码：❯ = 2 → 3 → 4 → 5 …              （正是用户截图的一串 ❯）
  新代码：❯ 恒为 1                          （修复）
```

复现要点：`sim.resize(..., fix_cursor=False)`——**还原"光标不跟随内容"的终端语义**
（xterm.js 类终端，含 Jupyter 终端、VS Code 终端；用户实际使用 Jupyter 终端运行 cbhcli）。
此前测试台默认会调用 `fix_cursor` 把光标"修回内容末尾"（模拟真实终端），
反而把用户终端的真实行为掩盖了，所以前几轮测试全绿、用户仍复现。

### 2. 根因

1. **光标根本不跟随内容**：终端 reflow（长行重折 + 滚屏）后，xterm.js 类终端的
   光标停在旧行 → `CPR 光标行` 完全不可信 → 旧实现算出的"旧区域顶"偏低，
   旧 `❯` 所在行没被清掉，每 resize 残留一个。
2. **区域内偏移用旧值**：多行输入在某宽度下折行数变化时，光标在区域内的偏移
   必须按**新宽度**重算（旧值会带来 ±1~N 行偏差：偏上擦内容、偏下留 ❯）。

### 3. 修复（`resize_fix.py` 第四轮重写）

1. **双路估算，按信号取用**
   - `est_cpr = CPR 光标行 − 偏移`，偏移用**干渲染**（离屏 screen 写入布局）按新宽度重算；
   - `est_prev = 上次区域顶 − max(0, 区域自身 reflow 增长 − 区域空白间隙)`（保守）；
   - `est_full = 上次区域顶 − 区域自身 reflow 增长`（终端底部固定/滚屏时的准确值）；
   - 判定：`CPR 行号 == 旧光标行`（光标根本没动）→ 该终端光标不跟随内容，
     用 `est_full`；否则用 `min(est_cpr, est_prev)`。CPR 不可用/超时 → `est_full`。
2. **reflow 增长估算**：按"样式相同的连续有内容行 = 同一逻辑行折行"分组，
   拼接后按新宽度重折；**只统计"真的会写进终端"的格子**（空白且样式无可见属性、
   如 `[transparent] class:last-line` 的补齐空格，渲染器不会写，不能算内容）。
3. 沿用第三轮硬约束：重绘范围 == 清除范围；渲染高度全程锁定；绝不主动滚屏。

### 5. 已知取舍

"光标不跟随内容"与"光标跟随但本次没发生位移"在 `CPR == 旧光标行` 时**信息上不可区分**，
因此新代码在后者（多为真实终端 + 区域内有空白间隙吸收折行的场景）可能**多清 1 行**，
表现为紧邻输入框上方 1 行内容的行尾被覆盖。相较旧版"每次 resize 残留一个 ❯ 且累积"，
该取舍明显更小；后续如需彻底消除，需要应用侧维护"已打印内容行模型"（本轮未做）。
