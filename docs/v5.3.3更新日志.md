# v5.3.3 更新日志

> 发布日期: 2026-09-12
> 主题: 会话加载全面提速（Web 卡顿修复）+ CLI `/resume` 恢复后回显历史对话

## 背景

用户反馈两个体验问题：

1. **CLI `/resume` 恢复历史会话后终端不显示历史内容** —— 消息虽已恢复进上下文，但界面上是空的，
   需要像 Web 那样把历史对话文字展示出来（继续对话前能对上上下文）
2. **Web 页面加载卡顿** —— 新建会话、恢复历史会话等操作要等 1 秒以上

### 卡顿根因定位（实测数据）

| 环节 | 旧耗时 | 说明 |
|------|--------|------|
| `WebChatSession.create()` | **0.9 ~ 1.7s** | 其中几乎全部是 `MCPManager._connect_all_servers()`（每次会话都重新 initialize 所有 MCP 服务器，网络握手 0.8~1.0s）；进程内首次另含 chromadb 初始化 0.77s |
| 恢复会话 `_load_session_core()` | ~0.9s | 内部同样调用 `create()` |
| 侧边栏 `list_sessions(500)` | 0.445s（cbhcli agent，509 个文件） | 为每个历史文件**完整解析整份 JSON**（含全部 messages，185MB） |
| 大会话 `usage_stats()` | 117 ~ 138ms | 每次调用都 tiktoken 重算全部消息（768 条 / 2MB） |

## 一、MCP 连接进程级缓存（核心提速，`core/mcp_manager.py` + `core/mcp_client.py`）

- **`_CONN_CACHE`**：进程内按「mcp.json 服务器配置内容」缓存已建立连接与工具定义
  （key 用**内容 hash** 而非 mtime —— 连接过程本身会重写 mcp.json，mtime 每次都变）；
  后续会话直接克隆客户端 + 复用工具定义注册，**零网络请求**
- **`MCPClient.clone()` / `reset_session()`**：复用一个已握手的 MCP 会话（共享 `Mcp-Session-Id`
  与 headers），但每个会话持有独立客户端对象（独立 JSON-RPC 请求 id 计数，避免并发 id 冲突）
- **失效与刷新**：配置内容变化（增删服务器 / 改 header / 启停工具）→ key 变化 → 自动重连；
  `/mcp refresh`（Web 刷新按钮）仍强制重连并刷新缓存
- **负缓存**：连接失败的服务器记录 120s 冷却，避免"每次建会话都卡在一个挂掉的服务器上"；
  冷却期后自动重试
- **会话失效自愈**（`core/mcp_tool_adapter.py`）：工具调用报会话相关错误（session/404/410/not found）时
  自动重新握手并重试一次（缓存让多个会话共享 MCP 会话后，服务器重启/会话过期需要这一步兜底）

## 二、服务启动后台预热（`web/server.py`）

`run_server()` 启动后立即拉起后台线程 `_prewarm_runtime()`：
初始化向量库 + 预连接各 Agent 的 MCP 服务器（写入连接缓存）。
用户第一次新建/恢复会话即命中缓存，不必等"进程内第一次"。

## 三、会话列表零解析（`core/session_history.py`）

- **只读文件头部**：元数据字段（id/title/created_at/updated_at/message_count/workspace）都在 JSON 开头、
  `messages` 之前，读取前 8KB 逐行解析即可（格式不符自动回退完整解析）
- **按 (mtime_ns, size) 缓存**：文件未变则零解析；保存/重命名/删除会即时刷新缓存条目
- 侧边栏（`/api/workspace/info`）与 CLI `/resume`、`/history` 共同受益

## 四、`usage_stats()` 签名缓存（`web/server.py`）

以「消息数 + 全部消息内容总长度」为签名缓存统计结果；追加消息 / 流式输出 / 压缩 / 工具变化
都会改变签名（`_rebuild_tools`、`chat_switch_model` 显式失效），命中时直接复用。

## 五、CLI `/resume` 恢复后回显历史对话（`commands/session_cmd.py`）

- 恢复会话后在终端回显历史：**用户消息**灰底高亮（与输入回显同款样式）、
  **AI 回复**用 `MarkdownStreamRenderer` 渲染（代码块/表格/列表/公式与实时回复一致）、
  **工具调用**折叠为一行摘要（`🔧 工具调用: read, edit, terminal，共 5 次调用`）
- 只回显 user/assistant 消息（tool 结果不展开、思考内容不显示）；
  默认回显**最近 20 条**、单条超长截断 1500 字符，头部标注总数与省略条数
- 回显失败不影响会话恢复本身（异常吞掉，仅提示）

## 十、发布后修复（同日）：所有交互式命令报 `is_done` 错误（`core/resize_fix.py`）

**现象**：CLI 里 `/resume`（进入交互选择菜单后）报
`命令执行失败: install_resize_fix.<locals>._render_wrapper() got an unexpected keyword argument 'is_done'`
—— 会话没有恢复；同类交互命令（`/undo-compress`、`/mcp add`、`/agent add`、`/model add` 等
所有走 `prompt_utils.ask_text` 的输入）同样中招。

**根因**：
- `resize_fix` 第四轮（v5.3.2 同版本迭代）把 `prompt_toolkit.renderer.Renderer.render`
  的 wrapper 签名写死为 `(self, app, layout)`，漏掉了 prompt_toolkit 的第三个参数 `is_done`
- `Application.run()` 收尾时**无条件**执行 `self._redraw(render_as_done=True)`
  （`application.py` 的 finally 块），当 `erase_when_done=False`（`prompt_utils` 的共享
  `PromptSession` 即默认值）时走 `renderer.render(self, self.layout, is_done=True)` → TypeError
- 该异常从 `Application.run()` 的 finally 抛出，**覆盖了用户输入结果**，因此表现为"命令执行失败"
- 主输入框（`ChatInputBox`）为何不受影响：它设了 `erase_when_done=True`，
  done 渲染走 `renderer.erase()` 而不是 `render(is_done=True)`

**修复**：`_render_wrapper(self, app, layout, *args, **kwargs)` 并原样透传给原始 render；
同时对 `_report_wrapper`、`_debounced_on_resize` 一并加 `*args, **kwargs` 透传，
避免 prompt_toolkit 后续版本再改签名时出现同类崩溃。

**验证**（pty 驱动真实 cbhcli，对照实验）：
- 修复前（旧安装版）：重现用户报错原文 `命令执行失败: ... unexpected keyword argument 'is_done'`
- 修复后（源码版 + 安装版）：`/resume` 菜单 → 选择会话 → 历史回显 → `✅ 已恢复会话（3 轮对话，12 条消息）`，
  无 `is_done`、无 `命令执行失败`、无 Traceback

**教训**：凡是 patch 第三方库的方法，签名必须用 `*args, **kwargs` 原样透传（或每次核对上游签名），
写死形参在库升级/未覆盖的调用路径上会静默埋雷；prompt_toolkit 的 `PromptSession`
务必注意 `erase_when_done` 对 done 渲染路径的影响。
