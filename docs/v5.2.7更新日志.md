## 一、CLI 思考显示重构（thinking_display.py v5：滚动窗口 + 破坏点防御）

### 1.1 修复的现象

用户报告：CLI 思考显示"有时候思考完会换行重复显示"：

```
💭 思考中... 5s
1. 用户发现页面行为异常？
💭 思考完毕 6s
1. 用户发现页面行为异常？      <- 同一段思考显示两遍
2. 用户只是确认状态
3. 或者用户指的是浏览器页面需要刷新（静态资源缓存）？
```

### 1.2 根因分析（v4.9.9 的 v2 方案缺陷）

v2 方案是"手动 ANSI 区域重绘"：维护一个 `[头行 + 最近8行内容]` 的屏幕区域，
每次 chunk 到达后 `\033[{N}A` 上移 N 行 + `\033[J` 擦除 + 重绘。它依赖一个
**隐式契约：区域存续期间没有其他输出把光标推走**。

该契约在真实环境中极脆弱，本次重复 bug 的实锤路径：

1. reasoning -> tool_calls（无 content）的流：思考区域存活期间，
   `ai_handler.py` 在流结束后构造 tool_calls 时打印 `\n🔧 工具名(...)`
2. 该 print 的 `\n` 把光标多推 2 行（区域下方）
3. 随后 `finish_thinking()` 的 `\033[{N}A` 上移数按旧 N 计算，到位错误
4. `\033[J` 只擦掉区域尾部几行，**区域头部（"💭 思考中... 5s" + 第1行）残留**
5. "💭 思考完毕"新区域画在残留下方 = 同一段思考显示两遍

### 1.3 为什么不用 rich.Live

用户提议 rich.Live 方案。调研结论：**rich.Live 内部同样是"上移 N 行 + 擦除"式
重绘**，与 v2 手动 ANSI 无本质区别：
- 流中第三方 print 推走光标 -> 上移错位 -> 残留（本次 bug 同款）
- 终端变窄后已打印长行被 reflow（1 行软换成 N 行），物理行数 > 记录行数，
  上移不足 -> 残留（v4.8.4 已在 Markdown 流式渲染上踩过同一坑）

### 1.4 v5 方案：滚动窗口重绘 + 破坏点防御清单（同版本内迭代）

显示形态（用户明确要求）：**有限行数滚动窗口 + 流式滚动**：

```
💭 思考中... 12s          <- 头行（1 物理行，秒数随 chunk 实时更新）
<最后 max_lines=8 行思考内容>  <- 滚动窗口：新行进来，最旧的行被顶出窗口
```

中间曾实现 v4 append-only（思考全文逐行打印 + 底部单行状态行），用户否决：
"思考内容每行全部显示了，而且不是有限行数的滚动窗口"。v5 恢复 v2 的窗口
重绘协议（上移 N 行 + 擦除 + 重画最后 8 行），叠加本版实锤修复的全部破坏点：

1. 🔧 工具行 print：ai_handler 已把 finish 提前到打印 🔧 之前（见 1.5）；
2. 复读警告 print（思考流中）：打印前调用 suspend_status() 擦除活动窗口
   → 警告行打在窗口外 → 后续 add_content 自动重建窗口；
3. resize 变窄：region_width 策略（窗口行宽 ≤ region_width=min(宽,100)；
   变窄时旧窗口行已被 reflow，放弃擦除留一次性快照，以新宽度重建，
   每次收窄最多 1 份快照，不会连续重复）；
4. 终端过矮（高度 ≤ max_lines+2）：收缩窗口行数 min(max_lines, 高度-2)
   （下限 3），防窗口本身超屏滚动导致擦除错位；
5. enabled=False（exec headless / 并行子 Agent）：完全 no-op（含 cleanup
   不写任何 ANSI，防输出捕获场景乱码）。

rich.Live 不采用的结论不变：其内部同为"上移擦除"式重绘，同样的破坏点
无法防御。

### 1.5 ai_handler.py 配合修改

- **finish 提前**：流结束（md_renderer.flush() 后）立即 `finish_thinking()`，
  移到打印 `🔧 工具调用行` **之前**（旧版在流末尾才 finish，正是本次 bug 的
  触发路径）；
- **复读警告防残留**：两处 `⚠️ 检测到...陷入重复` 打印前调用
  `suspend_status()`（擦除活动窗口，后续 add_content 自动重建）；
- 异常分支的 finish 条件从 `is_reasoning and is_thinking` 简化为 `is_thinking`。

### 1.6 接口兼容性（零改动调用方）

- `ThinkingDisplay(max_lines, label)` 签名不变
- `enabled=False` 完全静默：exec_runner 的 monkey-patch、subagent 并行禁用
  均兼容（cleanup 在 disabled 时也不写 ANSI）
- 新增公开方法：`suspend_status()`（语义：擦除活动窗口）

### 1.7 验证（微型终端模拟器 + PTY 真实终端）

自研 TermSim 微型终端模拟器（网格 buffer + 光标 + ANSI 上移/擦除/滚动解析）
驱动 14 项断言，验证最终屏幕状态：

- S1 20 行思考：最终屏幕恰显示最后 8 行（13~20），被顶出的行不在屏幕，
  头行"思考完毕"恰 1 次，无"思考中"残留；
- S2 本次 bug 场景（reasoning->tool_calls 无 content，finish 后打印 🔧）：
  三行思考各恰 1 次、🔧 行 1 次、无重复窗口；
- S3 复读警告 suspend + 窗口重建：警告行 1 次，内容行各恰 1 次；
- S4 多段思考（reasoning->content->reasoning 交错）：两段各自完整、
  两个"思考完毕"头行、无残留；
- S5 enabled=False：零输出（含 cleanup 不写 ANSI）；
- S6 矮终端（高度 8）：窗口收缩为 6 行，仍零重复；
- S7 cleanup（Ctrl+C）：擦除窗口无残留；
- S8 未换行尾巴 + 超宽行硬换行：正常显示。

PTY 真实终端（120x40）复跑 S1 场景：窗口重绘序列（\033[nA\033[J）21 次、
最终窗口恰好最后 8 行（13~20）、思考完毕在 🔧 之前。

⚠️ PTY 测试坑：pty.fork() 未设置 winsize 时终端宽度为 0，会触发收窄快照
分支（表现为逐行 append 而非窗口重绘），必须 fcntl.ioctl(TIOCSWINSZ)
设置窗口大小后再验证。

## 二、edit 工具五级宽容匹配链（file_edit.py）

### 2.1 背景

edit 工具"经常因 unicode 或字符幻觉不匹配报错"。v5.1.5 已有三层匹配链
（精确/空白宽容/Unicode 转义宽容）+ repr 诊断，但 LLM 的字符幻觉类型远不止
转义层级问题。**本次开发过程本身就是活案例**：连续多次 edit 失败，根因都是
形似字符幻觉：

| 文件实际字符 | LLM（本模型）幻觉输出 | 码点 |
|---|---|---|
| `→`（U+2192 单字符） | ASCII `->`（两字符） | 视觉无法区分 |
| `—`（U+2014 em-dash） | ASCII `-` 或"空格-空格" | 视觉无法区分 |
| `：`（U+FF1A 全角） | `:`（半角） | 视觉接近 |

结论：**LLM 从 read 输出复制字符时，对"单字符 Unicode 符号 vs 多字符 ASCII
组合"存在系统性幻觉，工具端只能靠更宽容的匹配兜底。**

### 2.2 五级匹配链（find_edit_matches 统一入口）

```
1. exact   精确匹配
2. flex    空白宽容（空格/非断行空格 U+00A0 互通）           [v5.1.5]
3. escape  Unicode 转义宽容（字面 \uXXXX 序列 ↔ 实际字符）    [v5.1.5]
4. fold    折叠归一化宽容（全角/半角、中英文引号、破折号家族、
           零宽字符）                                        [v5.2.7 新增]
5. fuzzy   difflib 相似度兜底（唯一高相似窗口自动采用）        [v5.2.7 新增]
```

#### 第 4 级 fold（折叠归一化，1:1 字符映射保位置精确）

折叠规则（两侧同折后匹配，命中区间经 pos_map 精确映射回原文）：
- 全角 ASCII（U+FF01-FF5E）→ 半角（含全角空格 U+3000 → 空格）
- 中文引号 `“”‘’` → 英文 `"'`
- 破折号家族 `– — ― −` → `-`
- 零宽/不可见字符（U+200B/200C/200D/FEFF/2060）直接跳过（文件有而 old_str
  没抄到的场景）

#### 第 5 级 fuzzy（difflib.SequenceMatcher 兜底）

- **探针预筛**：old_str 头/中/尾三个 ~10 字符片段行级定位候选窗口（3 万行
  文件 ~143ms，可控）
- 候选窗口 = 以命中行为结尾的 n_old 行窗口，逐窗计算 ratio
- **自动采用条件**：ratio >= 0.85 且 old_str >= 12 字符且**第二名 ratio 落后
  0.03 以上**（无歧义）→ 用文件实际文本替换，输出醒目提示
  `⚠️ 已使用模糊匹配（old_str 与文件不完全一致，已替换文件中最相似片段）`
- **歧义保护**：多个相近候选（如两处相似代码）不自动替换，错误信息列出
  疑似位置 + 相似度 + 实际内容 repr，引导一发命中
- 覆盖场景：`→` vs ASCII `->`（1:2 不保长，fold 无法覆盖，fuzzy 兜底）、
  `≥` vs `>=`、多点小幻觉叠加

### 2.3 错误诊断增强

未命中时错误信息新增：

```
[模糊匹配诊断] 最相似位置: 行 X~Y（相似度 87%）
  该处实际内容(repr): '...'
  （相似度已达标但存在并列候选或窗口歧义，未自动替换；请用 read 查看该行后按实际字符重试）
```

### 2.4 接口变更

- `find_edit_matches(content, old_str)` 返回值从 `(spans, matched_text)` 扩展为
  `(spans, matched_text, method)`，method ∈ exact/flex/escape/fold/fuzzy/none
- 唯一外部调用点 `tool_executor.py` 预览渲染同步更新（预览与执行结果一致，
  fuzzy 命中时预览显示的"原内容"就是将要被替换的文件实际文本）
- `EditTool.execute` 不再自行拼三级链，统一走 find_edit_matches

### 2.5 验证（11 场景）

精确回归 / fold 全角冒号 / fold 中文引号 / fold em-dash vs ASCII 连字符 /
fuzzy `→` vs ASCII `->`（本次开发亲历场景）/ fold 零宽字符 / 无匹配诊断 /
多匹配报错 / fuzzy 歧义不自动替换 / fuzzy 唯一高相似命中 / execute 端到端
fold 替换。全部通过。

## 五、经验沉淀

1. **上移擦除式重绘（含 rich.Live）的破坏点必须穷举**：任何第三方 print
   （🔧 工具行、复读警告）、任何 resize reflow 都会打破"上移行数 = 窗口物理
   行数"契约。滚动窗口形态下，防御 = ① 重绘路径内收口（所有流中 print 前置
   suspend_status / finish 提前）+ ② 变窄留快照重建 + ③ 过矮收缩窗口 +
   ④ 捕获场景 enabled 全静默。v4 append-only 曾试图用"无擦除"规避全部破坏点，
   但用户否决其显示形态（全文打印非滚动窗口）——**显示形态由用户决定，
   稳健性靠防御清单实现**。
2. **LLM 字符幻觉是系统性的**：单字符 Unicode 符号（→ — ≥）与多字符 ASCII
   组合（-> - >=）视觉相同，LLM 复制时必然偶发错乱；edit 类精确匹配工具的
   宽容链要覆盖"形似字符"维度（fold 处理 1:1 形似、fuzzy 兜底 1:N 形似）。
   对无法可靠输出的字符（本模型实测 → 输出不稳定），edit 的 old_str 用
   行尾短锚点避开，或用字面 `\uXXXX` 序列走转义宽容层。
3. **模糊自动替换必须有歧义保护**：ratio 阈值（0.85）+ 显著性差距（第二名
   落后 0.03）+ 最短长度（12 字符）三重门槛，并列候选降级为诊断信息。
4. **PTY 测试必须设置 winsize**：pty.fork() 未设置 TIOCSWINSZ 时终端宽度为 0，
   会触发收窄快照分支（表现为 append 式输出），测试结果失真。
