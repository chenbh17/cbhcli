# CBHCLI v5.4.4 更新日志

发布日期：2026-10-21
主题：Web 页面访问密钥门禁（页面锁）

## 背景

v5.4.0 引入设备级认证（`~/.cbhcli/auth.json`）后，Web 服务存在一个安全缺口：

- 设备未登录时，任何人打开 Web 页面只能看到登录界面（正常）；
- 设备**已登录**后，任何能访问该端口的人打开浏览器都会**直接进入主界面**——
  不需要知道密钥也能使用 Web 页面（模型配置、Agent、会话、文件管理全部可用）。

v5.4.4 增加**第二层认证：页面锁**。设备已登录时，浏览器必须输入
**本机当前登录账号的认证密钥**才能访问页面。

## 行为说明

| 设备状态 | 浏览器状态 | 页面表现 | 业务 API |
|---|---|---|---|
| 未登录 cbhcli | — | 现状不变：登录视图（服务器地址 + 密钥） | 401 `not_logged_in`（不变） |
| 已登录 | 未解锁（无 cookie） | 只显示密钥输入卡片 | 401 `page_locked` |
| 已登录 | 已解锁 | 主界面（不变） | 200，正常 |

细节：

- 解锁密钥**必须属于本机当前登录账号**（比对 `user.id`），其他账号的密钥返回
  `wrong_user`，防止他人拿自己的账号进入本机页面。
- 解锁凭据：HttpOnly **session cookie**（关闭浏览器失效）+ 服务端 **24 小时滑动过期**
  （每次请求续期；连续 24 小时无活动需重新输入）+ **7 天绝对上限**。
- WebSocket 同步受保护：未解锁连接会被 `close(code=4401)` 关闭。
- 页面锁未解锁时，`/api/auth/status` 只返回 `{logged_in, expired, page_locked}`，
  不暴露用户名/密钥前缀等身份信息。
- 设备登出（`/api/auth/logout`）会同时吊销全部页面会话。
- 账户弹窗新增「🔒 锁定此浏览器」按钮（立即回到密钥验证视图）。
- 服务重启后页面会话（内存）全部失效，浏览器需重新输入。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/web_auth/status` | `{gate_enabled, unlocked, user?, server?, ttl_seconds}`；未解锁不返回 user/server |
| POST | `/api/web_auth/login` | body `{key}`；成功 Set-Cookie；错误码 `invalid_key / disabled / wrong_user / not_logged_in / rate_limited / unreachable / timeout / protocol_mismatch` |
| POST | `/api/web_auth/logout` | 吊销当前浏览器页面会话 + 清 cookie |

未解锁访问业务 API：`401 {"error": "page_locked", "message": "需要输入认证密钥解锁本页面"}`

## 安全设计

1. **服务端强制**：HTTP 中间件 + WebSocket 端点双重校验，curl / 脚本直连同样被拦截。
2. **只允许本机账号**：解锁时校验返回的 `user.id` 与 `auth.json` 一致。
3. **不污染设备凭据**：`verify_only` 不签发 token、不写 `auth.json`、不写登录记录。
4. **Cookie**：`HttpOnly` + `SameSite=Lax` + `Path=/`（HTTPS 时 `Secure`），
   服务端只存 `sha256(token)`，页面会话仅在进程内存。
5. **限流**：同一 IP 每分钟最多 5 次失败验证（成功清零）。
6. **信息脱敏**：未解锁时不返回用户名 / 密钥前缀 / 策略。

边界说明：Web 服务为 HTTP 明文时，密钥与 cookie 可被同网络嗅探（与现有登录同级）；
需要更强安全应前置 HTTPS 反向代理。页面锁解决的是"同机/同网络的人打开浏览器即可使用"。

## 兼容性

- 设备未登录：行为与 v5.4.2 完全一致（现有登录视图）。
- CLI / `cbhcli exec` / Jupyter 插件：不受影响（中间件仅在 `cbhcli web` 的
  `run_server()` 挂载）。
- 管理服务端未升级（无 `verify_only`）：旧服务端会忽略该参数并签发 token，
  客户端不落盘，页面锁仍可正常工作（多产生一条未被使用的 token 记录）。
- 旧前端缓存：`index.html` 的 `?v=` 已升级到 5.4.4，强制刷新静态资源。

## 迭代（2026-10-21）：浏览器密码管理器自动填充

问题：页面锁的密钥输入框使用 `autocomplete="off"` 且不在 `<form>` 内，
浏览器虽然保存过密码，但无法把已保存的密钥自动填充到输入栏。

修复：

- 页面锁改为真实 `<form id="page-lock-form">`，密钥框 `name="password"` +
  `autocomplete="current-password"` + `autocapitalize="off"` + `spellcheck="false"`；
- 解锁按钮改为 `type="submit"`，`app.js` 绑定 form `submit`（preventDefault）后
  走原有解锁逻辑；单行输入框内 Enter 天然触发提交；
- 设备登录视图的密钥框同步改为 `autocomplete="current-password"`；
- 静态资源缓存参数 `?v=` 升为 `5.4.4.1`（强制浏览器加载新前端）。

提示：若浏览器仍未自动填充，手动输入一次密钥并在"保存密码"提示中选择保存
（或在浏览器密码管理器中编辑该地址已有条目），之后即可自动填充。

## 迭代（2026-10-22）：压缩后系统提示词位置修复（不升版本号）

问题：

- 上下文压缩把 `[历史对话摘要]` 作为 `role=system` 消息插在会话中间；多次压缩后
  头部还会累积多条 system 消息；
- 部分 OpenAI 兼容 API（如通义 / Qwen 端点）严格要求 system 必须位于消息列表开头，
  中间位置或多条 system 会直接 400：
  `"System message must be at the beginning."`；
- 表现为压缩过几次的会话继续对话时请求失败。

修复（`compressor.py` + `model.py`）：

1. **`compressor.py`**
   - 按 `SUMMARY_MARKER` 前缀区分「主系统提示」与「历史压缩摘要」；
   - 压缩后的消息列表开头只放主系统提示（**主系统提示始终在第一位**）；
   - 旧摘要内容原文并入本次新摘要（`【旧压缩摘要】` + `【本次新压缩摘要】`），
     整个会话始终保持「1 条主系统提示 + 至多 1 条摘要 system」，
     不再随压缩次数累积多条 system；
2. **`model.py`**
   - 新增 `_extract_text()`：兼容 `str` 与多模态 `list` 的 system 内容提取；
   - 新增 `_consolidate_system_messages()`：发送前把所有 system 消息按原顺序
     拼接为一条并置于列表首位（已是规范形态则原样返回）；
   - `_clean_messages()` 开头调用，`chat()` / `chat_stream()`（含 fallback 重试路径）
     全部生效，任何调用路径都满足「system 仅在首位」。

验证：16 项单元 / 流程测试全部通过（中间 system 合并、多模态合并、已规范形态不变、
首次压缩主系统在首位、二次压缩 system 恒为 2 条且旧摘要并入新摘要、
发送列表首条 system 且后续无 system）。
