发布日期：2026-10-25
类型：**Bug 修复 + 体验优化**（v5.5.0 全屏 TUI 的补丁版本）

## 一、上下文压缩（重写保留策略，对齐 v5.4.3 请求格式）

### 1. 压缩后"只剩最开始一轮"（严重）

**根因**：旧实现用 **"轮数 × 2 条消息"** 估算保留轮次，但一轮真实对话是
`user → assistant(tool_calls) → tool → assistant(tool_calls) → tool → … → assistant`，
常常十几条消息：

- `keep_recent=3` 实际只取**最后 6 条消息**，这 6 条通常整段落在某次工具循环中间
  （**一条 user 都没有**）；
- 再经 `_split_at_boundary` 调整（切点落在 assistant(tool_calls) 时向后跳过所有 tool），
  recent 会被吃成 4 条 / 2 条 / **甚至 0 条**；
- 实测 1245 条消息的会话：`keep_recent=3 → recent=4 条、user=0`；`keep_recent=1 → recent=0 条`。

**修复**：
1. 新增 `_turn_starts()` / `_select_turns()`：**按 user 消息边界切分"轮"**，
   `recent` 永远是"最后 N 轮用户请求 + 其完整工具链"；
2. 保留预算不足时**优先牺牲最早轮**（其内容已进入摘要），**保住最近对话**；
3. 压缩目标自适应：不小于「系统提示 + 摘要下限 + 最小保留」，且 ≤ 窗口 70%
   （实测某会话 system≈56k tokens 而 target=窗口30%≈38k，旧逻辑永远判"超目标"
   → 把保留轮一路压到只剩 1 条工具消息）；
4. 保留消息的 `reasoning_content` 直接丢弃（思考过程对续任务价值最低、占用最高）；
5. 单条截断下限 400→200 字符（tool_calls 200→100）。

**实测**（真实 1245 条消息会话）：`898,565 → 73,211 tokens`（57.2% 窗口），
**保留最近 3 轮用户请求**；合成 4/5/6/10 轮会话分别保留「最近 3 轮 / 早期1轮+最近3轮 / …」。

### 2. 消息顺序未遵循 v5.4.3（严格 API 会 400）

旧实现把摘要 system 消息 **append 在 early 之后**（位于对话中间），违反
"system 必须在列表开头"的约束（严格 API：`System message must be at the beginning`）。

**修复**：顺序固定为
```
[主系统提示...] + [摘要 system] + [最早轮] + [最近轮]
```

### 3. `/comp` 误报"上下文较短,无需压缩"

**根因**：轮数不多时 `keep_early + keep_recent` 覆盖全部轮 → `compress()` 直接返回
False 且 `last_error=None`，UI 只能显示通用文案。用户此时可能有几十万 token。

**修复**：
1. 轮数不足时**自动收缩"最早轮"**（`keep_early = min(keep_early, total_turns - keep_recent - 1)`），
   只要 > keep_recent 轮就能压缩；
2. 每次压缩**先清空 `last_error`**（避免显示上一次的旧错误）；
3. 无法压缩时给出具体原因（如"当前会话只有 3 轮对话（保留最近 3 轮就已覆盖全部）"）。

## 二、修复自动压缩 400：`Invalid \uXXXX escape`

**现象**（用户报告）：自动压缩时
`主模型调用失败: API请求失败: 400 - {"error":{"message":"Invalid \\uXXXX escape: line 1 column 527 (char 526)"...}}`

**根因**：`_cap_tool_calls()` 压缩时按**字符位置**直接切工具参数，再拼
`...[N 字符已截断]`——会把 JSON 切断在字符串/转义序列中间：

```
旧: {"content": "创建测试目录 ... 任务", ...   ← 被切成 \u...[339 字符已截断]
    → 非法 JSON → 再次发送时 API 解析 tool_calls 参数即 400
```

实测该会话历史里有 **8 条**这样的非法 `arguments`（`json.loads` 全部失败）。

**修复（两层）**：
1. **结构化截断**（`compressor._truncate_json_args()`）：能解析成 JSON 的，
   递归截断**字符串值**后重新 `json.dumps`；解析不了的整体替换为合法占位 JSON。
   **绝不返回半截原文**。
2. **发送前自愈**（`LLMClient._sanitize_tool_args()`，在 `_clean_messages()` 内）：
   遍历所有历史 `tool_calls.arguments`，`json.loads` 失败的替换为合法占位 JSON——
   历史坏数据、其它路径产生的坏数据都不会再触发 400。

## 三、CLI 输出渲染宽度统一（修"错行/错位"）

**现象**：AI 回复正文（Markdown）、子Agent状态板等文字输出在窄终端下错行；
edit/write/python 预览红绿错位（v5.5.0 已修预览，本次补齐其余）。

**根因**：全屏 TUI 主区文字宽度 = **终端列数 − 2**（最右 2 列预留，防宽字符压到
最后一列触发终端自动换行/滚屏）。rich 默认按**终端满宽**出图 → 最右 1~2 列被主区
折行折到**下一行最左侧**（终端折行从行首开始）。

**修复**：新增统一入口 `text_width.render_width(margin=1)`，
所有 rich 渲染/宽度计算改为按主区宽度：
| 模块 | 位置 |
|------|------|
| `core/markdown_renderer.py` | AI 正文 Markdown（每次渲染前刷新 Console.width，兼容 resize） |
| `core/tool_executor.py` | edit 差异预览 / write、python 代码预览（`_render_width()`） |
| `core/subagent.py` | 并行子Agent状态板（rich.Live） |
| `core/thinking_display.py` | 思考窗口宽度 |
| `core/app.py` | 欢迎面板（方框宽度） |
| `core/text_width.py` | 新增公共函数 `render_width()` |

**验证**：`tests/ui/check_preview_width.py`（主区 60/80/120 列 × 长中文行/超长代码行）
断言每行显示宽度 ≤ 主区宽度；Markdown 渲染实测 `console.width=117`（主区 118）。

## 四、选区保护（"选中后鼠标一动就消失"）

**原因**：终端收到应用输出时会刷新缓冲区并清除原生选区；而全屏 UI 在鼠标按下/释放、
轮末修格、状态栏「运行中」动画（10 帧/秒）、思考窗刷新（0.12s）时都会重绘。

**修复**：
1. 鼠标操作后 **0.6 秒「重绘静默期」**（内容照常进缓冲，只推迟绘制）；
2. 按住左键（可能在拖选）期间持续静默（最长 3 秒，防流式卡死）；
3. 静默结束后统一补一次重绘（`invalidate()` / `_schedule_full_repaint()` 同一入口）；
4. 补齐关闭 `?1015`（urxvt 鼠标编码），只保留 `?1000h`（点击/滚轮）+ `?1006h`（SGR）；
5. 滚轮不进入静默期（滚动跟随手指）。

## 五、滚动跟随（新行为）

| 场景 | 行为 |
|------|------|
| 用户发送消息（Enter 提交） | **自动回到底部（最新）** |
| 新内容到达且用户已上翻 | **保持用户当前阅读位置**（offset 同步补偿新增行数） |
| 用户手动滚动 | 位置保持不动（按用户意愿浏览） |
| 长时间无操作（25 秒） | **自动回到底部** |
| 贴底状态 | 新内容自动跟随（天然） |

实现：`_main_fragments()` 比较上一帧主区逻辑行数与折行宽度（宽度变化时不补偿，
避免 resize 抖动）；`_scroll()` 走 `_arm_idle_scroll_reset()`（25s 定时器）；
`_accept()` 提交时 `scroll_to_bottom()`；`Ctrl+Home/Ctrl+End` 同样接入。
