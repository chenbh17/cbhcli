# v5.1.6 更新日志

## 核心变更：上下文压缩机制四项优化

对标 Claude Code 三层压缩架构（Microcompact / Auto-compact / Manual compact）调研后，对 cbhcli 压缩链路做了四项优化：**修复 target_tokens 死参数**、**摘要提示词升级（9 章节结构化）**、**压缩可撤销（/undo-compress）**、**摘要输入保留工具调用链**。

---

## 一、修复 target_tokens 死参数（压缩目标 = 窗口 30%）

### 根因

`ContextCompressor.compress()` 声明了 `target_tokens` 参数但**函数体从未使用**（仅出现在 docstring 中）——压缩结果大小完全由摘要模型自由发挥决定，不可控。且所有调用点传入的是 `trigger_threshold()`（= 窗口 × 80%，即触发阈值本身），意味着**压缩后仍接近 80% 上限，会立即再次触发压缩**，形成重复压缩。

### 修复方案

| 文件 | 修改 |
|------|------|
| `constants.py` | 新增 `COMPRESSION_TARGET_RATIO = 0.3`（压缩后目标 = 窗口 30%） |
| `session.py` | `ContextWindow` 新增 `compression_target()` 方法（窗口 × 30%，与 80% 触发阈值分离） |
| `app.py` / `ai_handler.py` / `server.py` | 4 个调用点 `trigger_threshold()` → `compression_target()` |
| `compressor.py` | **target_tokens 真正生效**：① 摘要生成 `max_tokens` 按预算限制（目标 − 保留部分 token，下限 512）；② 压缩后校验总 token，超目标则**迭代降级保留轮数**（最近 3→2→1 重试） |
| `model.py` | 修复 kwargs 显式传入的 `max_tokens` 被模型配置覆盖的问题（`if self.max_tokens and "max_tokens" not in kwargs`） |

```
压缩前(80%触发) → 压缩后(目标 30%，摘要 max_tokens 受限，超目标迭代降级) → 有充足余量继续对话
```

## 二、摘要提示词升级（对标 Claude Code）

旧提示词为 5 点自由文本列表（用户需求/操作/文件/问题/状态），信息易丢失。新提示词：

```
CRITICAL: 你只能输出纯文本，禁止调用任何工具。你已拥有所需全部上下文。
你的回复必须包含两个部分：

<analysis>
先分析对话，识别：核心任务、关键决策、文件变更、用户指令、当前进度。
</analysis>

<summary>
按以下 9 个章节输出结构化摘要：
1. 任务目标：用户的核心需求
2. 整体架构：当前方案/模块设计
3. 文件变更：文件路径+关键改动内容
4. 决策：已确定的技术选型/方案
5. 已解决的问题：含关键错误信息
6. 全部用户指令：逐条列出
7. 约束：红线/限制条件
8. 当前状态：任务进行到哪一步
9. 下一步：待办事项
（要求：保留技术细节、丢弃试错过程、要点式描述、无内容写"无"）
</summary>
```

- **CRITICAL 级约束**：只输出纯文本、禁止调用工具（防止摘要请求被模型当作普通对话处理）
- **`<analysis>` + `<summary>` 双块**：先分析再总结，信息保留更完整
- **9 章节固定模板**：结构化输出保证可复用性
- `/comp 带指令` 的透传逻辑保留（优先级最高）

## 三、压缩可撤销（/undo-compress）

### 自动备份

`compress()` 在替换消息**之前**自动保存原始消息到：

```
workspace/history/compressions/<session_id>_<时间戳>.json
```

备份内容：完整消息列表（含 role/content/token_count/tool_calls/tool_call_id/reasoning_content/images）+ 压缩前后 token 数 + 时间戳。保留最近 **10 份**，自动清理。

### 新命令 /undo-compress

```
/undo-compress          # 交互列出最近压缩记录，输入编号选择
/undo-compress 2        # 直接恢复第 2 条记录
```

- 恢复：`session.replace_messages()` 还原原始消息 → 更新 context_window → **删除该备份文件**（一次性恢复，防积累）
- CLI 与 Web 的压缩（自动 + 手动）都会自动生成备份，均可恢复
- 恢复时显示 token 变化：`✅ 已恢复压缩前的上下文 (15,000 → 50,000 tokens, 2026-08-01 10:00:00)`

## 四、摘要输入格式改进（保留工具调用链）

旧格式只拼接 `role: content`，tool 消息丢失工具名和调用链，摘要无法理解工具执行序列。新格式：

```
[用户] 帮我写一个工具
[助手] 好的，我来写
[助手调用工具: terminal]
[工具 terminal 结果] ls -la 输出...
...
```

- tool 消息 → `[工具 <工具名> 结果]`（通过 tool_call_id 从 assistant 消息的 tool_calls 建立映射回工具名）
- assistant 带 tool_calls → `[助手调用工具: a, b]` 标记
- **大输出截断**：tool 消息 600 字符 / user·assistant 2000 字符（防止超大工具输出撑爆摘要请求输入）

## 七、经验教训（补充到长期记忆）

- **"死参数"是隐蔽 bug**：`compress(session, target_tokens)` 的 target_tokens 从未被使用，且调用点传的是触发阈值本身（80%），压缩后立即再次触发——**参数声明后必须确认函数体内真正消费它，调用点传入的值要与语义匹配（目标≠阈值）**
- **python 工具测试环境陷阱**：python 工具运行于已安装的 site-packages 版本，`sys.path.insert` 源码目录后 `import cbhcli_pkg` 仍可能命中旧包或触发循环导入（`core/__init__` → `app.py` → `compressor.py`）；可靠做法=① 用 `spec_from_file_location` 从文件独立加载被测模块（手动构造包 `__path__`）；② 或独立进程跑测试脚本，已安装包 + 仅源码版覆盖被改模块
- **import 时绑定 vs 运行时绑定**：`from X import ask_text` 是 import 时绑定，monkey-patch `X.ask_text` 对已导入模块无效，必须 patch 模块属性（`mod.ask_text`）
- **压缩目标必须显著低于触发阈值**（30% vs 80%），否则压缩后立即再次触发死循环

## 八、影响范围

- **CLI/Web 共用**：上下文压缩链路（自动压缩 / /comp / Web compress API / ReAct 循环内压缩）
- **兼容性**：压缩行为变化（目标 30%、9 章节摘要、备份落盘），但触发时机/保留策略不变；存量会话无感知
- **备份目录**：`workspace/history/compressions/`（新增，不影响 history/ 会话记录）
- **⚠️ 生效方式**：已打包安装 v5.1.6；运行中的 Web 进程需重启后新逻辑生效
