## 一、主区滚动条 + 滚轮灵敏度（需求①）

- **布局**：主区行改为 `VSplit([主区, 滚动条(width=1)])`，根部预留由 2 列改 1 列——
  主区文字宽度仍为 `cols-2`（`text_width()`/`render_width()` 全链路不变）；
  滚动条占 `cols-2` 列（`█` thumb / `│` 轨道，恒宽 1），终端最后一列永远留空
  （T-21 宽字符防自动换行不变式保持，`check_status_overflow` 断言同步更新）。
- **交互**：拖拽 thumb 按比例滚动；点击轨道 thumb 中心跳到点击处；滚动条列滚轮同主区。
  内容不足一屏时不显示。拖动/点击走 `invalidate(force=True)` 跟手重绘。

## 二、空闲自动回底：任何交互重置 + 2 分钟（需求②）

- `_IDLE_SCROLL_RESET_SEC` 25s → **120s**。
- **任何用户交互都重置计时**：按键（挂接 pt `key_processor.after_key_press` 信号）、
  鼠标点击/拖动/滚轮/滚动条（`_on_mouse_activity` → `_note_user_activity`）。
- **竞态修复（用户报"只按第一次滚动计时"的根因）**：旧实现在调用线程 cancel、
  再经 `call_soon_threadsafe` 到事件循环线程 schedule——两次快速滚动时第二次
  cancel 可能发生在第一次 `_schedule` 执行前 → 两个定时器并存、更早的先触发。
  现引入**代际号 `_idle_gen`**：每次 arm 递增，`_schedule`/`_fire` 校验代际，过期丢弃。
- ⚠️ **教训：pt 的 `Event.fire()` 以 `handler(sender)` 调用**——零参钩子签名会
  TypeError 并**杀死整个输入回调**（表现为"滚轮一次后键盘/鼠标全死"，且 traceback
  被 ScreenSink 吞进逻辑屏看不到）。钩子必须 `def _note_user_activity(self, *args)`。
  排查手法：给事件循环挂 `set_exception_handler` 日志才抓到真异常。
- 新增门禁 `tests/ui/check_idle_scroll.py`（常量/钩子/代际竞态单元 + pty 按键重置集成）。

## 四、鼠标直接拖选 + Ctrl+C 复制（需求④）

**为什么改**：Shift+拖动依赖终端原生选区——流式输出期间静默期（0.6s/3s）一过
选区就被重绘冲掉，且松手顺序（先左键后 Shift）易错。用户明确要求"直接拖动选中"。
（v5.5.0 曾实现应用内选中后被否掉回退；本次为用户重新明确批准。）

- **协议**：`_MOUSE_RESTRICT_SEQ` 增加 `?1002h`（按住拖动上报；仍不开 1003 any-motion）。
  xterm.js 语义兼容序列保持"先 1003l 再重发"。SUSPEND 返回后 `_mouse_modes_fixed=False`
  允许 after_render 重发（pt reset 会重新开 1003）。
- **应用内选区**（`shell.py`）：主区左键 down/move/up 维护
  `_sel = {a:(视觉行,列), b:(视觉行,列), width}`；渲染时选中片段加 `reverse` 高亮
  （`_split_select` 按显示列拆分，CJK 宽字符不拆、组合符跟随前格）；
  单击（无位移）= 取消选中；宽度变化/5000 行裁剪/清屏 → 选区自动失效；
  滚动/流式追加时选区跟随内容（绝对视觉行坐标 + offset 补偿）。
  Shift+拖动事件（带 SHIFT 修饰）交还终端原生，两套并存。
- **Ctrl+C 语义**：模态 > **有选区→复制**（状态栏提示"已复制 N 字符（通道）"，
  选区保留）> 无选区→原五级中断状态机不变。
- **剪贴板多通道**（新文件 `core/ui/clipboard.py`）：
  1. **Jupyter 桥文件** `~/.cbhcli/clipboard.txt`（0600 原子写）——实测 JupyterLab
     的 xterm.js **未注册 OSC 52**（grep 安装包 registerOscHandler 列表无 52），
     服务器侧 xclip 也到不了浏览器 → 由插件前端轮询写入浏览器剪贴板（见第五节）；
  2. **OSC 52**（kitty/WezTerm/Windows Terminal/iTerm2/Alacritty 等，SSH 可用；
     不支持的终端静默忽略；>100KB 跳过）；
  3. **系统工具** wl-copy/xclip/xsel/pbcopy（本地桌面会话，2s 超时）；
  4. 都不行时桥文件仍在，提示"已存 ~/.cbhcli/clipboard.txt"。
- 启动提示更新：`滚轮/右侧滚动条滚动历史；鼠标直接拖动选中，Ctrl+C 复制（无选中时 Ctrl+C 为中断）`。
- 新增门禁 `tests/ui/check_selection.py`（列提取/高亮单元 + pty：单行部分选中复制、

## 七、滚动条残影根因修复（2026-11-22 用户实测截图反馈）

**现象**（用户截图）：JupyterLab 终端里滚动条出现**多个分离的蓝色 █ 残影块、
两条不同列的灰色 │ 轨道、文字行右缘游离数字尾巴、行内容重叠错乱**。

**根因（pty 复现不出，必须在 xterm.js 实测才暴露）**：
prompt_toolkit 的差分重绘 `_output_screen_diff` 按**模型宽度**推进光标
（`current_pos.x += char_width`），再用相对移动（cursor_forward/backward）
定位下一个变更格。模型里 emoji=2 列（wcwidth/字素簇宽度），但 **xterm.js
实际把 emoji 渲染成 1 列** → 每写一个 emoji，终端真实光标比模型少前进 1 列，
**行内光标跟踪逐步失配** → 该行后续所有单元格（尤其最右侧的滚动条）写到错误列。
不同行 emoji 数不同 → 滚动条落在不同列 → 多重残影/双轨道；旧格未被覆盖 → 文字尾巴。
（纯 pty+pyte 复现不出：pyte 的 emoji 宽度与模型一致，无失配。）

**修复：emoji 宽度终端自适应**（`core/text_width.py`）
- 新增 `_EMOJI_WIDTH`（默认 2）+ `_is_emoji_cp`（emoji 呈现类码点范围）+
  `_cluster_width`：emoji 类簇按 `_EMOJI_WIDTH`，**CJK/几何符号/ASCII 不受影响**。
- `display_width` 与 pt 宽度缓存 `_ClusterAwareCache` 统一走 `_cluster_width`。
- **`probe_emoji_width()`**：进入界面前用 **CPR 光标位置差实测**终端对 🔧 的
  渲染列数（写 🔧 前后各查一次 `\x1b[6n`，列号差即真实宽度）→ xterm.js=1、
  多数终端=2 → `set_emoji_width()` 并清空 pt 缓存。**实测探测对任意终端都正确，
  无需 DA1/DA2 型号指纹**。探测字符用空格覆盖还原；`finally` 里 `tcflush(TCIFLUSH)`
  清空残留 CPR 字节，避免污染后续输入（实测 stray `1R2R` 会被 shell 当命令前缀）。
- `app.run()` 在交互 TTY 启动时调用一次（fullscreen/legacy 都覆盖；exec/web 非 TTY 跳过）。

**验证**：
- CDP 驱动真实 JupyterLab 终端（xterm.js）跑确定性 150 行 emoji 内容：
  滚轮上/下、resize 缩小/放大后再滚轮——**滚动条单一连续 thumb + 单轨道，
  文字整齐无残影**（修复前同场景多重残影/双轨道/错乱）。
- 新增门禁 `tests/ui/check_emoji_width.py`（mode 切换/CJK 不变/旗帜恒 2/pt 缓存刷新/probe 非 TTY 安全）。
- `tests/ui/` 全量 **28 套件通过**。
- ⚠️ 教训：**宽度模型必须与终端实际渲染一致**，否则差分重绘光标失配——
  这类 bug 在 pty/pyte（宽度自洽）里永远复现不出，**必须在目标终端 xterm.js 实测**。

## 九、粘贴图片报 400 "image format is illegal" 修复（2026-11-22 用户实测）

**现象**：CLI 粘贴图片 `[图片: 截图 ….png]` 发送后主模型报
`400 invalid_parameter_error: The image format is illegal and cannot be opened`。

**根因（双重 data URI 前缀 + MIME 硬编码）**：
- `attachments._load_image_b64` 原本返回**带前缀**的 `data:image/png;base64,xxx`；
- 但 `Message.images` 的约定是存**裸 base64**（image 工具/Web 都如此），
  `Message.to_dict` 会再包一层 `data:image/jpeg;base64,{img}`；
- 两者叠加 → `data:image/jpeg;base64,data:image/png;base64,xxx` **畸形 URL** → API 拒绝。
- 且 to_dict 硬编码 `image/jpeg`，对 PNG/GIF/WebP 的 MIME 也不正确。

**修复**：
- `attachments._load_image_b64` 改返回**裸 base64**（对齐 image 工具/Web 约定）。
- `session._image_data_uri(b64)`：按**魔数嗅探**真实 MIME（PNG/JPEG/GIF/WebP/BMP），
  不再硬编码 jpeg；已带 `data:` 前缀的输入直接透传（防二次包裹）。
  `Message.to_dict` 改用该函数 → 同时修好 image 工具/Web 的 PNG MIME。

**验证**：用用户真实图片 `截图 2026-08-14 23-06-06_2.png` 实测：
parse→裸 base64→to_dict 得 `data:image/png;base64,iVBOR…` 单前缀正确 ✓；
新增门禁 `tests/ui/check_attachments.py`（裸 base64/四种 MIME 嗅探/无双重前缀/引用解析）；
`tests/ui/` **29 套件全绿**；双环境重装 + Web 服务重启。

## 十、多图/混合粘贴 + 含空格路径识别（2026-11-22 用户确认补全）

**多图 + 图片文件混合**：本就支持（`parse_attachments` 收集所有 `[图片:]`/裸路径进
`images[]`，`to_dict` 生成多个 `image_url`；JupyterLab 粘贴收集剪贴板全部文件）。
实测 2 图 1 文件混合、3 图均正确。

**补全短板：含空格路径**（截图文件名常带空格，原裸路径正则按空格断词识别不了）。
`parse_attachments` 新增多格式路径识别（按序处理，统一 `_to_ref` 判定真实文件，
非文件一律不动；`_in_ref` 跳过已生成引用内的路径防重复）：
