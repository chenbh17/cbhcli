# v5.1.5 更新日志

## 核心修复：edit 工具 Unicode 转义宽容匹配 + 错误诊断增强

解决 LLM 调用 edit 工具时，old_str 含 Unicode 转义序列（如字面转义序列）被 JSON 编解码破坏转义层级、导致精确匹配失败的问题，使 edit 能"丝滑"处理含转义序列的文件。

---

## 一、问题定位：edit 为什么匹配失败？

### 错误现象

AI 用 edit 修改含字面转义序列（如 memory.md 中的 `→`）的文件时，反复报：

```
错误: 未找到匹配的文本: ...（old_str 显示为实际字符 → 而非字面转义序列）
```

### 根因：LLM 工具调用参数 JSON 转义链路

```
AI 生成 edit 参数（old_str 含字面转义序列）
  → 参数经 JSON 编解码：\uXXXX 被解析为实际字符（→）
  → edit 收到错误层级的 old_str（实际字符 →，1字符）
  → 与文件内容（字面转义序列，6字符）不匹配
  → 精确匹配失败，且无有效诊断信息 → AI 盲目重试陷入循环
```

**与 v5.1.2 同源**（LLM JSON 转义层级不可控），但位置不同：

| 版本 | 修复位置 | 场景 |
|------|---------|------|
| v5.1.2 | 消费端（ai_handler/server 的 arguments 解析后 `_fix_unicode_escapes`） | LLM **返回**的 tool_calls arguments 中双斜杠转义 |
| v5.1.5 | 匹配端（edit 工具的 `_find_unicode_escape_spans`） | AI **生成** edit 参数时转义层级被 JSON 链路破坏 |

**不是** read 工具的问题（read 只负责读取显示）；**不是** edit 精确匹配核心逻辑的问题（匹配本身正确，缺的是宽容匹配层和诊断层）。

## 二、修复方案（file_edit.py，219 → 326 行）

### 1. 三层匹配链

```
精确匹配 → 空白字符宽容匹配（原有） → Unicode 转义宽容匹配（新增）
```

新增 `_find_unicode_escape_spans()`，精确/空白匹配失败后自动尝试变体：

| 变体 | 函数 | 解决场景 |
|------|------|---------|
| 原文 | — | 正常匹配 |
| 字面转义序列 → 实际字符 | `_escape_to_char()` | 文件存实际字符（如 `→`），old_str 是字面转义序列 |
| 实际符号 → 字面转义序列（组合） | `_char_escape_variants()` | 文件存字面转义序列，old_str 是实际字符 |

- `_escape_to_char()`：正则匹配字面转义序列（反斜杠 + u + 4位十六进制）还原为实际字符
- `_char_escape_variants()`：只对**候选符号**（非 ASCII 且非 CJK 文字/标点）做组合转义，避免把中文整体转义导致变体无法匹配；候选符号通常 1~3 个，组合数可控
- **大小写兼容**：每个候选符号生成大写/小写两种十六进制形式（如 `00B1` / `00b1`），兼容文件中字面转义序列的大小写差异（实测 `±` 大写形式，旧逻辑只生成小写 `±` 导致匹配失败）
- 变体按优先级尝试，**首次命中的变体即返回**，避免不同变体匹配到不同位置造成歧义
- 匹配成功时输出提示：`ℹ️ 已使用 Unicode 转义宽容匹配（字面转义序列与实际字符互通）`

### 2. 错误诊断增强（匹配仍失败时）

新增 `_find_best_line_repr()`：找与 old_str 最相似的行，展示 **repr 对比**：

```
[诊断] old_str 的 repr（可看出转义层级差异）:
  '文件包含→测试'
[诊断] 文件中最相似的行（repr）:
  行 1: '文件包含字面转义序列→测试'
提示: 若 old_str 含 Unicode 转义序列或特殊字符，请对照上面的 repr 检查转义层级是否一致
```

AI 一眼看出转义层级差异（实际字符 vs 字面转义序列），可正确构造 old_str 或改用 read 查看原文。

### 3. 实现细节（避免源码转义歧义）

- 用 `chr(92)`（反斜杠）运行时构造转义序列，**源码中不写字面反斜杠序列**，杜绝"修工具时自身被转义问题困扰"（本次开发中实测：含 `\uXXXX` 字面的 old_str 经 JSON 传输必被破坏，故源码全部用 chr() 构造）
- 空白字符常量改用 `chr(0xA0)` 等运行时构造，避免源码含不可见字符

## 四、Web 端 reasoning_effort 配置优化（下拉框 + max 选项）

模型配置表单中，reasoning_effort 从手动输入框优化为**下拉框选择**：

- **选项**：不传 / `low` / `medium` / `high` / **`max`**（新增 max 档位，DeepSeek V4 思考模式支持 high/max）
- 存量配置值自动回显（非预设值也能显示，如已存的 `low`）
- thinking=off 时下拉框**自动禁用**（原有联动逻辑保留），保存时二次校验保留
- CLI `/model add`、`/model config` 提示同步更新为 `low/medium/high/max`

## 六、经验教训（补充到长期记忆）

- **LLM 工具调用参数中不能写包含 `\uXXXX` 字面序列的 old_str**——JSON 编解码必然破坏转义层级（生成端不可控），正确做法是让 edit 工具在匹配端做宽容变体匹配
- **修改含转义序列的代码/文件时，old_str 选择不含 `\uXXXX` 的短锚点**，或直接用 Python 脚本按字节处理
- **源码中表示字面反斜杠/Unicode 转义时用 `chr(92)` 运行时构造**，避免源码自身被转义处理（本次开发实测：write/edit 参数中 `→` 必被 JSON 解析为实际字符 `→`）
