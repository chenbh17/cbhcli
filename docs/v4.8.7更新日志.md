## 三、详细修改内容

### 3.1 `cbhcli_pkg/context/token_counter.py`（重写）

**问题 1：全局单例陷阱**

原代码 `get_token_counter()` 在 `app.py` 初始化时第一次调用没传 `model_name`，创建了 `_encoder=None` 的单例。之后切换模型时传了 `model_name`，但单例已存在不会重新初始化 → **tiktoken 从未生效，永远走粗略估算模式**。

```python
# ❌ 原代码（有 bug）
def get_token_counter(model_name=None):
    global _default_counter
    if _default_counter is None:
        _default_counter = TokenCounter(model_name)
    return _default_counter  # 第二次传 model_name 不会重新初始化！
```

```python
# ✅ 修复后
def get_token_counter(model_name=None):
    global _default_counter
    if _default_counter is None:
        _default_counter = TokenCounter(model_name)
    elif model_name and _default_counter.model_name != model_name:
        # 模型名称变化时重新初始化（修复单例陷阱）
        _default_counter = TokenCounter(model_name)
    return _default_counter
```

**问题 2：无 model_name 时也不初始化 encoder**

原代码 `__init__` 中 `if HAS_TIKTOKEN and model_name:` — 没有 `model_name` 时 `_encoder` 为 `None`，直接走估算。修复为无 `model_name` 时也用 `cl100k_base`：

```python
# ❌ 原代码
if HAS_TIKTOKEN and model_name:
    try:
        self._encoder = tiktoken.encoding_for_model(model_name)
    except KeyError:
        self._encoder = tiktoken.get_encoding("cl100k_base")
    # 没有 model_name → _encoder = None → 走估算

# ✅ 修复后
if HAS_TIKTOKEN:
    if model_name:
        try:
            self._encoder = tiktoken.encoding_for_model(model_name)
        except KeyError:
            self._encoder = tiktoken.get_encoding("cl100k_base")
    else:
        # 没有模型名称也用 cl100k_base，比估算准确得多
        self._encoder = tiktoken.get_encoding("cl100k_base")
```

**问题 3：消息结构开销缺失**

原代码每条消息只算 `content` 的 token，遗漏了 role 标记、tool_calls JSON 外壳、tool_call_id 等结构开销。新增 `count_message_tokens()` 方法：

```python
# 新增结构开销常量
MESSAGE_OVERHEAD = 4        # 每条消息: <im_start>{role}\n{content}<im_end>\n
TOOL_CALL_OVERHEAD = 3       # tool_calls JSON 结构外壳
TOOL_CALL_ID_OVERHEAD = 3    # tool_call_id 字段
REPLY_OVERHEAD = 3           # 对话回复前缀

# 新增方法：计算单条消息的 token（含结构开销）
def count_message_tokens(self, msg) -> int:
    # 兼容 Message 对象和 dict
    total = MESSAGE_OVERHEAD
    total += self.count_tokens(content)
    if tool_calls:
        total += TOOL_CALL_OVERHEAD
        total += self.count_tokens(json.dumps(tool_calls, ensure_ascii=False))
    if tool_call_id:
        total += TOOL_CALL_ID_OVERHEAD
        total += self.count_tokens(tool_call_id)
    if reasoning_content:
        total += self.count_tokens(reasoning_content)
    return total

# 重写 count_messages_tokens：使用 count_message_tokens
def count_messages_tokens(self, messages: list) -> int:
    total = REPLY_OVERHEAD
    for msg in messages:
        total += self.count_message_tokens(msg)
    return total
```

**其他小改动**：
- `count_tokens()` 新增空字符串检查：`if not text: return 0`
- `_estimate_tokens()` 新增空字符串检查
- 新增 `import json`（用于序列化 tool_calls）

**改动 4：新增 `_check_and_compress_in_react()` 方法**（第 306-345 行）

```python
def _check_and_compress_in_react(self, round_idx: int):
    """在 ReAct 循环中检查上下文使用量，超过阈值时自动压缩。
    压缩策略与 app.py 一致：保留最早2轮 + 最近3轮，中间部分生成摘要。
    压缩后 session.messages 被替换，下一轮 LLM 调用将使用压缩后的上下文。
    """
    if not self.context_compressor or not self.context_window:
        return
    if not self.auto_compress:
        return

    # 使用 token_counter 精确计算（含消息结构开销）
    total_tokens = self.session.get_total_tokens(self.token_counter)
    self.context_window.update(total_tokens)

    if not self.context_window.needs_compression():
        return

    # 上下文接近上限，执行压缩
    print(f"\n{self._c_dim}📦 上下文接近上限 ({self.context_window.get_status_text()})")
    print(f"{self._c_dim}   正在自动压缩上下文...{C_RESET}")

    target_tokens = self.context_window.trigger_threshold()
    success = self.context_compressor.compress(self.session, target_tokens)

    if success:
        new_tokens = self.session.get_total_tokens(self.token_counter)
        self.context_window.update(new_tokens)
        print(f"{self._c_dim}   ✅ 上下文已压缩 ({self.context_window.get_status_text()}){C_RESET}")
    else:
        print(f"{self._c_dim}   ⚠️  压缩失败（消息太少或生成摘要异常），继续执行{C_RESET}")
```

## 四、功能详解

### 4.1 ReAct 循环内自动压缩

**背景问题**：原代码中自动压缩只在 `_handle_ai_request()` 开头（用户下一次输入消息时）检查。但 ReAct 循环本身可能多轮工具调用导致上下文溢出，API 返回 `context length exceeded` 错误，任务被中断。

**解决方案**：在 ReAct 循环每轮 LLM 调用之前检查上下文使用量，超过阈值时自动压缩，压缩后继续执行任务。

**工作流程**：

```
ReAct 循环（每轮开始）
  │
  ├─ _check_and_compress_in_react(round_idx)
  │    ├─ 检查 context_compressor / context_window / auto_compress
  │    ├─ 精确计算当前 token（含消息结构开销）
  │    ├─ needs_compression()? (usage >= 80%)
  │    │   ├─ 否 → 跳过，继续执行
  │    │   └─ 是 → 调用 context_compressor.compress()
  │    │        ├─ 保留最早2轮 + 最近3轮
  │    │        ├─ 中间部分用 LLM 生成摘要
  │    │        ├─ 替换 session.messages
  │    │        └─ 更新 context_window token 计数
  │    │
  ├─ messages = session.get_context_messages()  ← 使用压缩后的上下文
  └─ _get_ai_response(messages, round_idx)     ← 继续执行任务
```

**覆盖范围**：
- ✅ CLI 端主 Agent（`ai_handler.py`）
- ✅ CLI 端子 Agent（`subagent.py` + `delegate_task.py`）
- ✅ Web 端（`server.py`）

### 4.2 Token 计算精度修复

**问题 1：全局单例陷阱**

| 步骤 | 代码位置 | 调用 | 结果 |
|------|----------|------|------|
| 1 | `app.py __init__` 第276行 | `get_token_counter()` | `_encoder=None`（无 model_name） |
| 2 | `app.py _init_session` 第546行 | `get_token_counter("glm-5.2:cloud")` | 单例已存在，**不会重新初始化** |
| 结果 | — | — | **tiktoken 从未生效，永远走估算** |

修复后：`model_name` 变化时重新初始化单例。

**问题 2：消息结构开销缺失**

| 消息类型 | 原计算 | 修复后新增 |
|----------|--------|------------|
| 所有消息 | `count_tokens(content)` | `+ MESSAGE_OVERHEAD (4)` |
| assistant + tool_calls | `+ count_tokens(json(tool_calls))` | `+ TOOL_CALL_OVERHEAD (3)` |
| tool 结果 | `count_tokens(content)` | `+ TOOL_CALL_ID_OVERHEAD (3)` + `count_tokens(tool_call_id)` |
| assistant + reasoning | `count_tokens(content)` | `+ count_tokens(reasoning_content)` |
| 整个对话 | — | `+ REPLY_OVERHEAD (3)` |

**精度对比**：

```
旧方式 (累加 token_count):  49 tokens  ← 严重偏低
新方式 (count_message_tokens): 88 tokens  ← 含结构开销
差异: +39 tokens (44.3% 更准确)
```

**估算 vs tiktoken 对比**（修复前走估算，修复后走 tiktoken cl100k_base）：

| 文本 | 估算 | tiktoken | 偏差 |
|------|------|----------|------|
| 你好世界 | 2 | 5 | -60% |
| 请帮我读取文件 /media/.../ai_handler.py | 24 | 37 | -35% |
| def compress(self, session, target_tokens): pass | 12 | 10 | +20% |
| 上下文接近上限 (上下文使用: 102400 / 128000...) | 16 | 27 | -41% |
